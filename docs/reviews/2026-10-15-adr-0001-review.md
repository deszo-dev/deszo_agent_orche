# ADR-0001 review

Date: 2026-10-15  
Subject: [ADR-0001: External workflow authoring through the runtime API and a shared MCP bridge](../adr/0001-external-workflow-authoring-api-and-mcp.md)  
Verdict: **Sound direction; not ready to accept.** The architecture is the right one: one runtime-owned HTTP contract, one stdio bridge, guarded saves, and durable change events. Two security boundaries are stated as goals without a mechanism that can meet them (ADR1-01, ADR1-02). Four smaller gaps should be closed before Stage 1 contracts start.

## What was checked

The ADR's factual claims were compared with the current code and with the vendors' MCP pages it cites.

## Findings

### ADR1-01 (high): the "management bridge never reaches managed execution" guarantee has no workable mechanism for Antigravity, workspace-scoped configs, or Inherit

The ADR makes isolation a release blocker but leaves the mechanism to later verification. The facts available now show which parts will fail:

- **Antigravity:** `buildInvocation` in [adapters.mjs](../../runtime/core/adapters.mjs) passes **no** restriction flags for Antigravity, even in Restricted mode. Antigravity's MCP page documents no per-invocation switch to disable configured servers, only a persistent `disabled` field. A bridge a user registers globally for Antigravity authoring would load in every Antigravity Agent node and Map role.
- **Codex:** `--ignore-user-config` addresses `~/.codex/config.toml`. Whether it also suppresses a trusted project's `.codex/config.toml` is unverified.
- **Workspace-scoped configs travel with the work:** `.mcp.json`, `.codex/config.toml` and `.agents/mcp_config.json` are project files. Map tasks run in copied work directories, so a user who registers the bridge at project scope (the scope the ADR's setup guidance is most likely to recommend) carries it into managed execution. Claude's `--strict-mcp-config` covers this; the other two may not.
- **Inherit profile:** this opt-in exists precisely to load the user's native configuration. The ADR does not say whether Inherit is incompatible with an installed bridge, filters it, or warns.

Recommendation: decide the mechanism in the ADR rather than in Stage 5, using layered defenses. A configuration-only guarantee cannot hold for Antigravity.

1. **The bridge refuses inside managed execution.** The runtime sets a marker (for example `DESZO_MANAGED_INVOCATION=<runtimeInstanceId>`) in the environment of every provider invocation. The bridge exits with a typed refusal when it sees the marker. Stage 5 must verify that each CLI passes the parent environment through to stdio MCP children. If a CLI scrubs the environment, the runtime has to reject management calls from managed sessions another way, such as a separate per-invocation token scope.
2. **Dispatch preflight.** The runtime checks the known global and workspace MCP files of the selected provider and work directory for the Deszo bridge entry point. It fails dispatch with a typed diagnostic rather than silently proceeding.
3. **Inherit is stated explicitly.** Either the bridge is disallowed under Inherit by the same preflight, or Inherit accepts the exposure with a recorded warning on the invocation.
4. **Setup guidance recommends user/local scope, never project scope**, and says why.

### ADR1-02 (high): untrusted run output reaches an authoring session that holds `start_run`

`read_artifact` and `list_run_events` return content produced by Full Access agents and by checks of the user's project. The same MCP session has `put_workflow` and `start_run`, and a started run executes Full Access CLI processes. The ADR says workflow content "cannot … claim that a user authorized execution". That constrains Deszo, but the party actually deciding is the authoring client's model, and it reads that content as context. The only remaining gate is each host client's tool-permission prompt, and users commonly auto-approve MCP tools.

Recommendation:

- Make execution tools opt-in per bridge registration (for example `--allow-execution`). Without it, `start_run` and `stop_run` are not registered at all. The authoring-only default covers the D19 request (describe a pipeline and have the workflow appear in the app).
- Optionally add a runtime setting requiring that externally created runs be confirmed in the Deszo window. Command receipts and pending-run state already make that representable.
- Wrap artifact and event payloads in tool results as data with explicit provenance (run, node, attempt). Never return them as free text that could pass for instructions.

### ADR1-03 (medium): the receipt fix is scoped to run creation and Stop, but the gap is in the shared helper

The same `idempotent()` helper serves settings updates, Context-binding acknowledgement, Context chat (which also captures a run), node Stop and recovery. Fixing only the exposed commands leaves the others restart-unsafe and creates two command boundaries. Fix the helper once: run `fn()` and the receipt insert inside one `store.transaction(...)`. Nested calls already flatten (`transaction` returns `fn()` when `inTransaction` is set), so `captureRun` needs no change. Keep `after` (dispatch) after commit. The v3 save path then reuses the same helper with its precondition check inside the transaction.

### ADR1-04 (medium): the v2 save retirement needs a complete writer inventory and an ordering constraint

The ADR says v2 endpoints stay available, then retires `PUT /api/v2/workflows/{id}` with `410`. That deliberate break is acceptable, but the plan should list every writer it breaks and every internal path it must not break:

- **Callers of the v2 save:** [App.tsx](../../src/App.tsx), [smoke.mjs](../../scripts/smoke.mjs), [pilot.mjs](../../scripts/pilot.mjs) and the test helper [helpers.mjs](../../runtime/tests/helpers.mjs). Several tests also call it directly (`engine.test.mjs`, `pipeline.test.mjs`).
- **Pending validation depends on the old route:** the real-provider rerun recommended in the [RERUN-04 resolution](../pilots/2026-10-14-pilot-rerun-resolution.md) runs `scripts/pilot.mjs`, which saves through v2. Either complete that rerun before cutover, or ship the upgraded script as a new file so the recorded pilot tooling stays reproducible.
- **Internal system writer:** the Context-chat system workflow is saved by the engine itself (`putWorkflow(..., { kind: 'system' })`). The ADR should state that system workflows are outside the revision/precondition contract, or define their revision handling.
- **Workflow-adjacent writes:** Cache pins (`PUT …/cache-pins/{nodeId}`) are keyed by workflow and node but are not workflow revisions. Say whether a pin survives a revision that changes or removes its Cache node, so "no write entry point bypasses preconditions" has a defined boundary.

### ADR1-05 (medium): an external client cannot create a workspace, so a first run from a client is impossible on a fresh install

The tool list exposes `list_workspaces` but not workspace creation, and `start_run` requires an existing workspace ID. This may be the right boundary, because choosing a Full Access working directory is a high-trust act. State it as deliberate, and specify the diagnostic: no workspace exists, so the user must create one in the Deszo window. Otherwise Stage 5's "create/edit a mixed-provider workflow … observe the result" scenario can pass while the "when the user's instruction includes execution" path fails on every fresh install.

### ADR1-06 (low): smaller contract gaps for Stage 1

- **Authoring event retention** is referenced ("if retained events no longer cover a cursor") but never defined. Specify the retention rule, or state that events are retained indefinitely like receipts.
- **`storeId` uniqueness:** a copied or restored store keeps its persistent ID. Two running instances could then present the same identity, and the bridge's wrong-store check would accept the wrong one. Pair `storeId` with the descriptor's absolute root, or document the copy rule.
- **Node prerequisite:** the desktop app launches the runtime with `node` from `PATH` ([main.rs](../../src-tauri/src/main.rs)), and the bridge needs Node too. Generated client configuration should name the absolute Node executable the app uses. Each client spawns stdio servers with its own environment, whose `PATH` may lack Node 22 or resolve a different version.
- **ETag and MCP null:** the HTTP form uses `If-None-Match: *` for create; the MCP form uses `expectedEtag: null`. The schema must make the field required and nullable, so a client omitting it gets `precondition_required` rather than create semantics.

## Recommended path

Amend the ADR for ADR1-01 to ADR1-05, keep it **Proposed**, and accept it after the amendment. ADR1-03 can be fixed independently of this ADR; it is a latent defect in the existing v2 commands.
