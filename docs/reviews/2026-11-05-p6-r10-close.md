## 1. Result

1. **Critical (code-established, not executed): repairable Engine code does not need reflection to reach the Host's P6 switch.** The Engine holds the lifecycle client as `this.lifecycleClient` (`engine.mjs:136`, set from `runner.mjs:144`). Engine code already calls `this.lifecycleClient.p6Call(...)` (`engine.mjs:249`). The bridge's `p6Call` allowlist admits `engine.stage` and `engine.switch` for any caller in the process (`lifecycleBridge.mjs:104-108`). The Host accepts a self-consistent staged package with the requested digest and does not check P5 acceptance (section 5). A repaired Engine that calls `engine.stage` and `engine.switch` directly bypasses the consumer and its P5 check. This is the most serious finding and it does not depend on R10.
2. **R10 reproduces on the real `p6Consumer.mjs`, `p6Builder.mjs` and Node v22.20.0.** A reflected `Function` imports the same module instance the entry point uses (R10-1). Code that holds that instance can bind a builder to any Engine-like object, which the registry accepts because it is keyed only by object identity (R10-2). It can also invoke the protected builder export with no caller check (R10-2). An unaccepted run is refused at the consumer's run-link check (`p6Consumer.mjs:349-351`). The P5 acceptance check (`:397-401`) was not reached (R10-3).
3. **`--disallow-code-generation-from-strings` closes only the reflected `Function` route** (EvalError, measured). `vm.runInThisContext` and `require(esm)` still run under it (measured). Separately, the flag stops the protected graph from loading, because `schemas.mjs:79` runs `ajv.addSchema`, which compiles the meta-schema during import. The per-schema validators are compiled lazily (`schemas.mjs:86,103`).
4. **Narrowing the registry closes one substitution path.** The lifecycle capability, `vm`, `require(esm)` and the direct Engine route in item 1 remain open. A Host-side P5 check would read Store evidence, and in-process code can write the Store.
5. **Decision C is required.** The lifecycle capability and the P5 acceptance writes must leave the repairable process (section 9). ADR-0011 is amended (its section 8). P6 release acceptance stays blocked.

### 3.4 Gate context (A) and installed context (B)

- **Context A (P5 candidate verification).** Candidate tests run in a separate verification process. The probe ran in a plain process of the same kind. The verification child was not instrumented. Whether it can reach a production Store, a Host bridge or the control channel is **not established**.
- **Context B (installed Engine).** The installed successor runs `runner.mjs`. Module evaluation order is deterministic. `runner.mjs:8` statically imports `engine.mjs` and `runner.mjs:23` imports `p6Consumer.mjs`, and both finish evaluating before the body runs. ## 9. Selected disposition: Decision C

Decision C is required, because the authority and the repairable code share one trust domain. The minimal architecture, with the three requirements the review added, is recorded in ADR-0011 section 8.3:

- **Two principals.** The lifecycle capability for stage and switch, the custody commands that mutate state, and the P5 acceptance writes move to a **trusted control process** that does not execute candidate code.
- **Role-separated capabilities.** The Engine still needs read-only lifecycle calls: `runningSourceRelease` and `runningSourceInventory` (`engine.mjs:245`, `:328`), and `engine.switch_status` (`engine.mjs:249`). So either the Host issues separate role capabilities, or the Engine's client loses `p6Call` for stage and switch and loses the mutating custody commands. The current single capability cannot express this.
- **Authenticated Store records.** The Engine writes the Store, so the control process cannot trust a plain reading of it. P5 acceptance records need an authenticator (for example a MAC) with a key only the control process holds.
- **Host-spawned control process.** The Host, not the Engine, starts the control process, so that the Engine cannot choose it.
- **Narrow channel.** The Engine requests a P6 operation over a channel whose only request is "activate run R". The control process verifies the request against the authenticated records and runs the consumer.
- **Host admission.** The Host accepts `engine.stage` and `engine.switch` only from the control process's capability. It still verifies package bytes and the Shell identity. It does not read the Store.
- **Hardening.** The Engine process runs with `--disallow-code-generation-from-strings` and precompiled validators, including the `addSchema` path at `schemas.mjs:79`. This is not the boundary.

Decision C does **not** close, by itself: Context A (candidate tests could reach the control channel or the Store), or the `node:child_process` route (section 10). Both need their own containment.

This is more than a fix to `p6Consumer.mjs`. It changes the process split and the capability model, so it is not implemented here. The brief forbids adding a process without demonstrated need. The need is demonstrated by sections 3–5.

## 10. `node:test` and `node:child_process` resolver disposition

- `CODE_LOADING_BUILTINS` (`p5Gate.mjs:301`) does not include `test`, and it does not include `child_process`. The P5 causal reproducer imports `node:test`. The earlier refusal, which broke the happy path, has been removed.
- `node:test`: it is a test runner that can load files in a test context. A subject module can already reach `vm`, so refusing `node:test` removes no authority. The resolver is a source-review aid, not a runtime boundary.
- `node:child_process`: the resolver accepts it. The reflection probe records it as accepted (route R9, `reflection-routes-probe.txt`). A child process receives no lifecycle bridge, because the bootstrap is deleted from the environment on read (`lifecycleBridge.mjs:61`) and the capability lives in memory. A child can still write the Store and the staging directory. So `child_process` is an open route, not a closed one.
- The boundary test asserts that the strict resolver refuses a `createRequire` import, a dynamic import, `import.meta.resolve` (direct, computed and aliased), `eval`, `new Function`, `process.mainModule` and reflective constructor reads (`p6-builder-boundary.test.mjs:166`, 12/12 pass). It does not test `vm` or `child_process` by name.

## 11. Protected-control integrity evidence

- `P6_PROTECTED_CONTROL_PATHS` is unchanged. Autonomous Repair cannot modify `runner.mjs`, `p6Builder.mjs` or `p6Consumer.mjs` through the Gate, and the builder boundary suite passes 12/12.
- Source protection does not restrict runtime import. The probe imported the protected modules by reflection in the same process. Protected-source integrity and runtime capability isolation are separate properties, and only the first is established.

## 12. Builder and Consumer capability evidence

- The builder is callable by any code that can import its module (R10-2 builder export: the call reached the function body and refused its own input with `p6_build_invalid_id`).
- The consumer's guard (`p6_builder_unavailable`) runs before the operation intent, the build and Host staging. It is correct, and it is not an authority boundary.
- A registered builder can be bound to any Engine-like object (R10-2). The binding is therefore not a credential.

## 13. Host and Store authorization evidence

- `engine.stage` / `engine.switch`: no P5 proof (section 5; `lib.rs:1860-1868`, `engine_switch.rs:277,424`).
- `verify_build` / `verify_build_artifact_set` (`lib.rs:1262-1297`) verify the package against its self-described artifact list, the marker rules and the source inventory. They do not verify against an accepted P5 digest.
- The Store is an in-process SQLite file. The Host has no independent read of P5 acceptance.
