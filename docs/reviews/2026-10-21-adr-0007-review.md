# ADR-0007 review

Date: 2026-10-21  
Subject: [ADR-0007: Event-driven Judge attention and compact evidence](../adr/0007-event-driven-judge-attention-and-compact-evidence.md)  
Verdict: **The direction is right, and the ADR is honest about its limits.** It requests the Judge only for decisions, keeps routine work inside the Developer/Watcher loop, and makes compact evidence a verifiable projection of the full audit. It also refuses to claim a wake-up path that has not been demonstrated. It is not ready to accept:

- the wake-up mechanism, the only part that delivers the benefit, is left entirely open, and it interacts with ADR-0001's managed-invocation refusal;
- once periodic attention is removed, the Watcher alone decides whether the Judge is ever involved, and the ADR defines no deterministic backstop against a Watcher that never escalates;
- the baseline numbers motivating the change are not recorded anywhere a reader can verify.

## Findings

### ADR7-R01 (high): choose the wake-up architecture, and note that a runtime-initiated Judge turn cannot use the bridge

§3 rightly requires a verified mechanism by which an event starts a Judge turn in the registered external chat, with no operator message. MCP results, notifications and SSE do not start turns in Codex. In practice there are only a few candidate mechanisms, with very different consequences, and the ADR should choose among them rather than defer the whole question to "the selected adapter":

1. **The runtime resumes the Judge session itself**, for example `codex exec resume <session>`. This makes Deszo a Judge dispatcher, which §3 forbids. More concretely, a provider process the engine starts carries `DESZO_MANAGED_INVOCATION`, so the resumed Judge's bridge would refuse every tool and the Judge could not read evidence or submit a decision.
2. **The ADR-0006 persistent worker is the adapter.** It blocks deterministically on the durable outbox with no model inference, and on a request it starts one model turn in the registered Judge session as a host-side process outside the runtime's marker. This fits "a deterministic event listener may wait… without model inference". It reuses the existing worker, budget ledger and least-privilege tool profile, and keeps the runtime out of model dispatch.
3. **A client-native background or scheduled resume feature**, if the exact Codex version offers one and it can be tested.

Option 2 is the only one the current architecture already supports in principle. The ADR should adopt it as the intended path, with option 3 as an alternative to verify. It should also state two concurrency rules:

- a woken turn must not run concurrently with the user typing in the same chat session;
- the turn's cost is charged to the ADR-0006/ADR-0003 aggregate budget as a controller-model call.

Without this decision, Stages 1 to 3 can be engineered completely and still deliver nothing.

### ADR7-R02 (high): no deterministic backstop exists for a Watcher that never escalates

Today the periodic semantic acknowledgement is the only thing that guarantees a model above the Developer/Watcher loop looks at the run. This ADR removes it. After that, the Judge sees a run only if the Watcher returns something other than `CONTINUE`, the engine raises an operational alarm, or budgets run out.

A mis-calibrated, prompt-injected or simply weak Watcher can therefore keep returning `CONTINUE` with plausible "next actions" while the Developer makes no progress. The loop then runs until `maxIterations` or `maxActiveMinutes`, or, under ADR-0006, until the session's aggregate budget is spent. §1 handles unchanged retries only for `BLOCKED`.

Recommendation: add engine-side, deterministic attention triggers that do not depend on the Watcher's judgement, and list them in §1 alongside the operational events. Examples:

- the same check fails with an unchanged failure signature across N consecutive iterations;
- an iteration produces no candidate diff, or the identical diff;
- the Watcher repeats the same next action;
- a declared fraction of the loop or aggregate budget is consumed without `READY_FOR_REVIEW`.

These produce a typed `no_progress` attention request, and the thresholds come from captured policy. Add an acceptance criterion: a Watcher fixture that always returns `CONTINUE` must still reach the Judge within the published bound.

### ADR7-R03 (medium): record the baseline where it can be verified

The motivation, and criterion ADR7-12's comparison, rest on the figures "781 journal events, 689 log events (88.2%), 21 saved observation batches". These figures appear in no evidence receipt. The cited control review supports the observation qualitatively only.

Add an evidence receipt under `docs/reviews/evidence/` (or `docs/pilots/evidence/`) recording:

- the run and store identity;
- the journal frontier;
- the query or method used to count events by type;
- the definition of an "observation batch".

ADR7-12 then compares against a reproducible baseline rather than a number in prose.

### ADR7-R04 (medium): the pending-request deadline needs an explicit outcome with no Judge, and the terminal-handoff case already exists

- **What happens when the deadline expires.** §4 offers "the captured escalation/Stop or a durable quiescent wait". For the Fixer, the loop's `maxActiveMinutes` keeps running only while work is active, so a quiescent wait could hold a run open indefinitely, consuming ADR-0006 permission time but no budget. State the default:
  - after the response deadline, a pending request moves the run to `waiting_for_user`, the existing state, with the request visible in Deszo;
  - once the session's authorization expires, ADR-0006 revocation semantics apply;
  - there is no unbounded "quiescent" running state.
- **Terminal handoffs.** A `succeeded` Fixer run that ends with `ESCALATE` already has no live work to block, and the ADR correctly routes the decision into a linked continuation. Say explicitly that in this case the response deadline governs only how long the request stays actionable before it is marked stale. A late decision then requires a fresh request built against the current state.

### ADR7-R05 (low): smaller points

- **Projection cost.** The compact projection must account for every event in its frontier, with classification, counts and digests, including in long runs. State its incremental computation: the projection is maintained per stream, with grouping updated as chunks commit, so a request never rescans the full journal. Then the ADR-0002 runtime-liveness stop (15 s) cannot be tripped by building an attention payload. The 64 MiB bundle measurement from ADR-0002 shows how such stalls were handled before.
- **The Judge is a Codex chat.** That is a property of this deployment, not of the design. Phrase the contract as a registered external controller session, with Codex as the first verified adapter, so a Claude Code or Antigravity Judge needs only adapter verification rather than an ADR change.
- **ADR7-01 measurement.** "Enough healthy elapsed time to cross the legacy attention interval" should name the interval being crossed. ADR-0002 fixes no default and lets Stage 1 measure it, so cite the value in force for the test.

## Recommendation

Decide ADR7-R01 (adopt the ADR-0006 worker as the wake-up adapter, with its concurrency and budget rules) and ADR7-R02 (deterministic no-progress triggers, with a fixture). Record the baseline (ADR7-R03) and the deadline semantics (ADR7-R04). Keep the ADR **Proposed** until then. Current ADR-0002/ADR-0006 attention behavior remains authoritative, as the ADR itself states.
