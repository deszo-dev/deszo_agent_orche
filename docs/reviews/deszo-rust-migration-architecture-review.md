# Deszo Rust migration — independent architecture review

## 1. Executive verdict

**`ARCHITECTURE REVIEW BLOCKED`**

Keep the two-backend-process direction. A maintainer-owned Rust Host and a separately replaceable, contained Rust Engine are the smallest credible arrangement for the Owner's Rust mandate and autonomous A → B → C. Removing Node and the Engine's direct lifecycle authority simplifies the shipped system. It also concentrates more authority and failure modes in the Host, while adding toolchain distribution, sandbox policy, and two durable state domains. The rewrite is a substantial migration.

The current proposal cannot be accepted as a preservation design. Host Admission expressly accepts candidates without evidence that an eligible Parent's designated Judge authorized the Repair. The Repair Gate and Judge can also be bypassed as workflow steps by submitting a candidate early. The design leaves Workflow resource grants without a trusted issuer, derives a compile-time build identity from post-build outputs, and promises successor continuity without checking or materializing the next enrolled slot. Cutover can admit two writers and promises rollback on evidence that proves only part of compatibility. These defects survive a successful containment experiment. Correct the contracts before implementing the affected interfaces. ## 4. Host and Engine complexity

The Host remains focused if its remit is authority over launches, protected transitions and durable selection. Admission should have internal boundaries for authorization, jobs/evidence, and protected state/reconciliation, with no dependency on Engine scheduling or a full workflow interpreter. In-process modularity keeps one authority for Stage/Commit. Ordinary Git, provider parsing, planning, non-protected Judge work, and product/API decisions can stay safely repairable within their assigned resource scope. The Engine can still damage its own Store and data it is permitted to write. The proposed architecture can guarantee product parity for supported Engines and bound a hostile Engine's privileged effects. It cannot enforce honest scheduling, honest ordinary history or correct ordinary Judge behavior against arbitrary replacement code solely by containing it. Scope that distinction explicitly.

The estimate of 12–13k Host lines against about 7.8k is a sizing hypothesis. It omits part of the protected Parent witness, multi-root permission enforcement, answer validation and cross-state recovery. A thread plus panic handling covers a bounded class of failures. It leaves process-wide resource exhaustion, aborts, deadlocks and shared-state corruption. Admission should have bounded frame and object parsing, job/resource quotas, short authority-state critical sections and a lifecycle/Stop path that stays responsive during admission. Revisit process isolation if such a failure is demonstrated and a separately constrained identity or restart boundary would address it. A line count alone is weak evidence for another trusted service. [Design 02 §3](../system-design/rust-migration/02-target-architecture.md#3-host-responsibilities-bounded) · [Design 03 §7](../system-design/rust-migration/03-trust-boundaries.md#7-limits-that-no-mechanism-removes) · [Design 08 §§2, 5](../system-design/rust-migration/08-alternatives-and-tradeoffs.md#2-comparison)

The inherited Engine channel and protected state are justified. The current bridge can send privileged commands to a Host dispatcher authorized by a shared capability. The closed Engine catalog removes that direct path when paired with actual containment. Keep the catalog narrow, with an explicit privilege matrix, versioning, per-operation ownership and priority/backpressure for Stop and custody control versus SSE, artifact bytes and job output. Reuse G0 and Custody. `slots.json` and successor records can be projections of the authority journal/selector. One logical job launcher suffices. The 11 crates mostly reflect domains, deployment units and tooling. Protocol, Store, workflow and separate binaries have distinct contracts. Provider and Git libraries can start as Engine modules if there is no separate consumer or dependency boundary. Resolve the `deszo-domain` destination named in 01 §2 against 02 §5. Keep protected protocol and canonical vectors small enough that ordinary product changes rarely need a Host release. ## 6. P2 authorization analysis

**P2 authorizes the Repair to start. P5 accepts a completed candidate for installation.** The current workflow Judge's `request_repair` is checked against the captured failure context and profile. The Engine checks a runnable immutable Parent and Repair, the exact failed node and P3 outcome revision, enrollment, isolation and Judge identity. It records authorization, link and Parent suspension. The protected Gate binds the exact Repair link, enrollment, input artifacts, enrolled Gate Attempt and successful Developer candidate. P6 subsequently requires the same accepted link and current retained, eligible handoff. These are implemented product checks within today's Engine trust model. They do not establish independent authority over a hostile Engine. [Judge action](../../runtime/core/workflowJudge.mjs#L498) · [P2 start and durable link](../../runtime/core/linkedRepair.mjs#L968) · [P5 Gate authorization](../../runtime/core/p5Gate.mjs#L754) · [P6 current eligibility](../../runtime/core/p6Consumer.mjs#L171) · [ADR-0010 §5](../adr/0010-p6-trusted-build-activation-rollback.md#5-automatic-pipeline-and-exact-switch-boundary)

04 §2.2 expressly accepts a Repair the Engine started “for no good reason” if verification and the acceptance Judge pass. At `ClaimSlot`, all lineage IDs are labels. A running enrolled Engine can invent those IDs, consume a permanent slot, submit a technically good commit and reach G0 without a Parent decision. A later Judge reviewing that commit cannot establish the earlier authorization. This is a deliberate mechanism in the proposal and a change without a recorded Owner decision. Superseding ADR-0010's authority placement does not authorize removing its P2 eligibility requirement. [04 §§2, 10](../system-design/rust-migration/04-self-repair.md#2-engine-requests-to-admission) · [ADR-0012 §§5.4, 7](../adr/0012-rust-first-backend-and-engine-lifecycle.md#54-self-repair-model-and-host-admission-authority)

The smallest correction is a **single-use, Host-issued protected Repair authorization**. At protected Parent admission, bind the authenticated launch to the root, generation, Parent publication/snapshot, captured policy and Run identity. When the Engine schedules the designated Parent Judge, have Host custody attest the invocation from the enrolled role/profile and capture its typed decision on the specific eligible incident. Define the small checkpoint witness needed to bind the failed attempt, outcome and revision to that Parent using trusted observations and to fence it when required. Bind the ticket to that decision, the pinned Repair publication, profile, link, suspension/eligibility checkpoint and scope. Consume it atomically with slot claim. Require its lineage through Gate, acceptance and switch, with durable revocation. A Host receipt that simply signs an Engine Store row or Engine-generated digest proves receipt of the assertion and cannot establish its facts. If a protected incident class cannot provide the necessary independent evidence, specify its supported scope or take any behavior change to the Owner. Preserve the ordinary P2 scheduler, and keep full Parent graph interpretation in the Engine. No new Owner approval is needed per Repair. ## 7. Workflow Full Access

Treat Full Access as a Workflow resource contract. The immutable publication pins a versioned declaration or digest and allowed resource bindings, including named roots/repositories, modes, tools, network, and any permission to use provider configuration. At launch the Run captures the effective concrete subset and its digest or durable Host scope reference. Binding a symbolic resource resolves it to a verified physical identity at admission. Current revocations may narrow or stop execution under a documented rule. Widening requires an authenticated Owner action within the publication contract or a new publication. Preserve the historical Run's captured scope, including after revocation. The Owner clarification settles the meaning of Full Access. Legacy launch mapping and provider availability remain choices in OD-1. [Design 02 §7](../system-design/rust-migration/02-target-architecture.md#7-platform-layout) · [Design 03 §§3, 7](../system-design/rust-migration/03-trust-boundaries.md#3-capability-matrix) · [09 §2, OD-1](../system-design/rust-migration/09-open-decisions.md#2-owner-decisions)

The Host must enforce the grant or authenticate a narrower binding from Owner-approved policy. An Engine-written publication or Run UUID cannot extend an OS permission. `Custody::Reserve` should reference a Host-issued scope; check executable identity, cwd, all physical roots, grants and child inheritance. Reserve overlapping mutable roots across jobs until custody proves drain. Separate concurrent Run grants, Repair slot grants, and preflight grants by effective OS principal or equivalent. A long-lived Engine given the union of Run grants can act across them. Keep ordinary file and Git operations in bounded jobs when they need per-Run authority, or explicitly specify a fixed Engine resource scope authorized by the Owner. Exclude Host state, credentials and private slots even through a parent root, reparse point, alias or inherited ACL. Tool/config discovery and credentials require narrow brokered or isolated configuration; a whole home-directory grant defeats this boundary. [Design 03 §§2–4](../system-design/rust-migration/03-trust-boundaries.md#2-principals) · [Current Custody reserve and launch](../../lifecycle-host/src/custody.rs#L835)

This changes the current launch model. The Run currently selects a primary `workspaceId`; the provider adapters use different CLI restrictions, including Codex workspace-write in Custody and bypass flags on other paths. A primary cwd can remain a convenience. A supported Workflow should also run practical multi-repository development with shared roots outside it, spawned compilers and scripts, dependency access where granted, and provider sign-in/resume. PR-2's one edit in one root is insufficient. Test concurrent overlapping and disjoint Runs, child tool access, Git/worktree metadata, credentials and network within policy, denials outside it, native CLI sandbox compatibility, and release/recovery of ACL grants. Move that evidence before the affected ordinary provider milestone as well as P5. For old publications preserve snapshot bytes and use an explicit legacy binding rule or Owner binding at launch. ## 9. Self-Repair continuity

The Host can independently verify protected paths and Git bytes, observe contained jobs, run the enrolled acceptance Judge, and record immutable acceptance. It can then build the accepted tree twice from pinned inputs and automatically activate the exact package. ## 12. Alternatives

| Option | Trusted surface, runtime and recovery | Delivery, portability, autonomy and maintenance |
|---|---|---|
| **A. Host with Admission + contained Rust Engine** | One trusted lifecycle/eligibility owner and one primary Engine protocol. Larger Host fault domain. Sandbox, parsers, custody and state reconciliation remain material. | Preferred once corrected. Native targets, per-platform containment and pinned Cargo infrastructure. High rewrite cost, lower long-term backend runtime diversity, and A → B → C through the Host. |
| **B. Host + Control + Engine** | A same-privilege Control adds IPC and restart reconciliation with little authority benefit. A distinct restricted identity could isolate parser crashes/resources and reduce direct Host access. It would still participate in trusted acceptance. | Concrete justification would be a demonstrated isolation need that bounded jobs/in-process modules cannot meet. Same sandbox, build and Engine port work plus Control protocol and package compatibility. Autonomous updates still possible. |
| **C. Shared Rust code or multirole distribution** | Shared code/build tooling and separate process identities are compatible. A shared replaceable image for both roles would let the release mechanism replace Host code. A pinned Host copy and independently selected Engine restore A's authority and recovery boundaries. | Engine maintenance and normal modes can share a binary with enforced grants. Sharing sources offers reuse without extra IPC. Merging Host with Shell ties lifecycle to WebView faults and window lifetime. |
| **D. Node + ADR-0011 historical baseline** | Reuses product code and esbuild. Current release block and existing trust model remain relevant. A secure baseline also needs actual containment, protected acceptance, credential separation, recovery and Node/transport feasibility. | Smaller parity rewrite and existing tests, extra Node packaging/loader/runtime maintenance and still platform-specific containment. Could support autonomous repair after its own gates. The Owner's Rust backend decision rules it out as a final architecture. |

The design correctly prefers A over adding a service without an enforcement or availability benefit. Its statement that Control necessarily has the Host's OS privilege overstates the case. ADR-0011's Control design used a distinct principal. The cost comparison should include that limited fault-isolation value and the additional protocol and recovery obligations. - **Failure / correction.** A large Git export or stalled stream monopolizes Host resources during an Owner Stop, or a port drops hard Custody deadlines as a side effect of preserving progress-driven execution. Document fault containment limits and panic strategy, bound untrusted work, protect the lifecycle control path, and keep existing deadlines, capture safety and workspace holds. Test stalled readers, resource exhaustion and injected admission failure before relying on in-process isolation. **Owner decision** none. A separate constrained process is an optional response if measured failure isolation requires it.

## 17. Final recommendation

Return ADR-0012 and the design set for correction while retaining Option A. The next design needs a closed account of who authorizes protected Repair, when its real Gate and Judge run, how each Run receives OS authority, what a build and successor attest, and how the selector and installer recover. The decisive acceptance evidence is a Host-witnessed A → B → C from two genuine Parent incidents, with an isolated preflight, reproducible builds, a coherent upgrade, and the same contract enforced on refusals and restart.
