# ADR-0006 review

Date: 2026-10-20  
Subject: [ADR-0006: Time-bounded autonomy and application lifecycle control](../adr/0006-time-bounded-autonomy-and-application-lifecycle.md)  
Verdict: **The requirement is well understood and the boundaries are careful. Not ready to accept.** The design has the application under development enforce the authority that permits its own replacement. It also leaves open who holds which credential across a host-driven restart. Both must be decided before the lifecycle host can be specified. Three further medium findings concern bootstrap, the worker's own residual risk, and whether the controller needs to be the application under test at all.

## Findings

### ADR6-R01 (high): the rebuilt application enforces the authority that permits its own replacement

In the motivating scenario, the session repairs and rebuilds **Deszo itself**, then launches the new build under the persisted policy. Per §2, though, the runtime is what derives each run approval and grant from the policy: it matches scope, reserves budget, issues grants and serializes against expiry. Every one of those checks lives in the code the session is allowed to change. A repair that edits, by mistake or under injected instructions, any of the following produces a rebuilt application that enforces a weaker policy than the one the user approved:

- `supervision.mjs`, the grant or confirmation paths;
- the scope table in `runner.mjs`;
- `supervisor.rs`;
- the policy matcher.

§7 forbids the candidate build from modifying "its supervising host". The policy enforcement, however, sits in the candidate, not in the host.

Recommendation:

- **Put enforcement in the trusted host.** The host holds the policy and decides each automatic approval: scope, expiry, revocation and the budget ledger. It is not rebuilt by the session. The candidate runtime requests decisions and executes the grants it receives. The ADR-0002 native deadlines remain the backstop.
- **Make authority code a mandatory stop point.** Classify the authority, scope and containment paths as ADR-0003 project-declared critical areas for Deszo, so that any candidate touching them falls outside the standard autonomous profile and waits for a user decision before rebuild or switch.
- **Verify the build manifest before launch.** The host checks the manifest of the build to be launched against that rule, so a build whose authority code changed is not started automatically.

### ADR6-R02 (high): credential custody across a host-driven restart is undefined

ADR-0001 gives the first-party token to whichever process **launches** the runtime, over its private stdout pipe. ADR-0006 has the host stop and start the application. Two different outcomes are possible, depending on what the host launches:

- **The host launches the runtime directly.** The host then holds the full first-party token: settings, workspaces, approvals and the confirmation toggle. That is far broader than the policy, and it falls outside "does not expose first-party credentials" (§8).
- **The host launches the Tauri application, which launches its runtime.** The first-party token stays in the Tauri supervisor. The host must then authenticate to the new runtime with a separate, policy-scoped credential that the new generation can verify, and §2's "registered controller identity" has to be defined in those terms.

Choose the second option, and specify:

- which secret proves the host's identity to a fresh runtime generation;
- where it is stored, for example DPAPI-protected and per user;
- how the runtime limits it to the policy's operations;
- that a fresh generation refuses it once the policy has expired or been revoked.

### ADR6-R03 (medium): the host's bootstrap and lifetime are unspecified

The host must outlive Deszo, but the application Job is kill-on-close with no breakaway allowed. A host started by Deszo would therefore die when Deszo exits. The ADR needs to state:

- **How the host starts.** For example, a per-user startup entry or scheduled task, or a launch with `CREATE_BREAKAWAY_FROM_JOB` together with `JOB_OBJECT_LIMIT_BREAKAWAY_OK` on the application Job. The latter weakens the crash backstop for that one child and must be justified.
- **Where its binary lives.** It must sit outside the repository build outputs, so a session build cannot replace it (the §7 promise).
- **How it is installed, upgraded and removed.**
- **How the minimal status and revocation surface is reached while Deszo is closed**, for example a tray icon or a small local page.

### ADR6-R04 (medium): the persistent worker is an unattended Full Access agent; state its residual and limit its tools

For up to twelve hours, the worker reads untrusted run output (ADR-0001), approves its own in-scope runs, edits Deszo source, builds and launches applications, with no human in the loop. Policy scope is its only guard. Running as the same OS account, a worker CLI with shell access can also read or alter "protected host-managed storage", because DPAPI decrypts for any process of that user. It can also edit its own MCP or client configuration.

Recommendation:

- **Run the worker without general shell or file tools.** It acts only through the bridge and host operations, which are themselves scoped by the policy. Source repairs run as ordinary managed workflow roles under the engine's review and acceptance contracts, not as worker edits.
- **State the residual explicitly.** A same-account process that is deliberately subverted can tamper with local policy storage. The design defends against accidental and injected misuse through the narrowed tools and host-side enforcement (ADR6-R01). It does not defend against the user's own account.
- **Count controller-model invocations** in the ADR-0003 aggregate budget and show them separately in the session index, since they consume quota with no workflow output.

### ADR6-R05 (medium): consider separating the controlling Deszo from the application under test

The Context assumes that updating the application under test replaces the controller, which forces restart continuity, run interruption and grant re-derivation. The ADR-0005 default, however, is a separate preview environment. For the shadcn/ui pilot and similar Deszo-on-Deszo work, the host could:

- keep the **controlling** Deszo, which runs the workflow, stable for the whole session;
- launch the **candidate** build as a separate instance with its own data root, install directory and ports for checks and native UI tests.

That removes most of §5's mid-run restart path:

- the workflow run is never interrupted by its own rebuild;
- the controller's MCP endpoint never disappears;
- rollback concerns only the preview.

Switching the controller would then be a rare session-boundary operation. The ADR should either adopt this as the default, keeping the controller switch as an explicitly scoped exception, or explain why the controller must be the application under test.

### ADR6-R06 (low): smaller points

- **Implementation branch.** Remove the branch name from the Implementation line and §9. An architecture record should not bind implementation to a branch. Track that in the status record or the PR.
- **Time across reboots.** Monotonic clocks do not survive a reboot. Record the last observed wall-clock time durably. On startup, treat a wall clock earlier than that record as a rollback: block dispatch until reconciled, and charge the gap as elapsed time, as the ADR's "conservatively" intends.
- **Native UI automation.** It acts on the user's live desktop. Specify that the session does not drive UI while the user is active, for example by requiring the dedicated session or a user-selected "unattended" state, and that focus-stealing input is part of the authorized scope shown at activation.
- **Rollback and migrations.** The store already writes a backup before migrating. Name that backup, or an explicit snapshot taken in restart phase 1, as the rollback data source. State that a rollback restores the matching snapshot and never opens a newer store with an older build.

## Recommendation

Decide ADR6-R01 (host-side enforcement) and ADR6-R02 (credential custody) in the ADR. Settle ADR6-R03 and ADR6-R04, and take a position on ADR6-R05, since it may remove most of the restart machinery. Keep the ADR **Proposed** until then.

R03 factual clarification: the inspected [Tauri code](../../src-tauri/src/main.rs) creates the kill-on-close/no-breakaway Job and assigns the spawned Node runtime. Its descendants inherit containment. This does not itself prove membership of Tauri or every other helper it might launch; the earlier statement that every process Deszo starts must belong to this Job is too broad. The selected SCM/task bootstrap still needs direct native membership/lifetime evidence and does not rely on a breakaway change.

The previous concurrency, time, ambiguous-effect and independent-evidence requirements remain in force. Sections 2 and 9 retain serialized host authorization/reservation, native admission fencing, no generic exactly-once claim, deterministic fault injection and criterion-to-independent-evidence coverage. Architecture/documentation resolution does not close the implementation gates or supersede the original review history.
