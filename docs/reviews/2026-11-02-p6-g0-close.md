## 4. ADR-0010 Alignment

ADR-0010 previously described a single-file model where a pending switch operation would be embedded directly into `active.json`. The implemented, tested, and reviewed Rust Host instead maintains:
- `.deszo-host/active.json` as the committed release pointer (`buildId`, `digest`, `generation`, optional `committedOperationId`).
- `.deszo-host/profiles/<profile>/lifecycle.json` as profile-scoped durable state housing `engineOperation` for in-flight operations and recovery.
- `.deszo-host/operations.ndjson` as append-only audit event journal.

Rather than introducing unnecessary state migration risk or redesigning working code, ADR-0010 Section 7 was updated to accurately specify this coherent architecture. The exact ownership boundary, commit boundary, and restart reconciliation invariants are now fully synchronized across all architecture and contract documents.

## 5. Authoritative Selector & Pending-Operation Model

The definitive source of truth across all lifecycle entities is established as follows:

| Entity | Source of Truth | Verification & Commit Boundary |
|---|---|---|
| **Current committed Engine** | `.deszo-host/active.json` (`ActivePointer.build_id`) | Only modified during atomic replace at commit |
| **Active package digest** | `.deszo-host/active.json` (`ActivePointer.digest`) | Verified before commit and during Host startup |
| **Lifecycle generation** | `.deszo-host/active.json` (`ActivePointer.generation`) | Advances to `candidate_generation` on commit |
| **Commit record** | `.deszo-host/active.json` (`committed_operation_id`) | Single atomic write; releases Store guards |
| **Pending switch operation** | Profile `lifecycle.json` (`engine_operation`) | Bound to `operation_id` and `request_fingerprint` |
| **Previous Engine identity** | Profile `lifecycle.json` (`from_build_id`) | Checked against active build before staging |
| **Candidate Engine identity** | Profile `lifecycle.json` (`to_build_id`, `package_sha256`) | Verified package in staging root and `versions/` |
| **Operation phase** | Profile `lifecycle.json` (`phase`) | Tracks progression: `staging` → `staged` → `fenced` → `a_stopped` → `guarded` → `preflight_running` → `preflight_passed` → `committing` → `committed` → `verified` (or `fallback`, `rolled_back`, `abandoned`, `held`) |
| **Restart reconciliation** | `engine_switch::reconcile_at_start` | `active.json` is commit authority; uncommitted phases safely recover to A or hold fail-closed |
| **Event audit** | `.deszo-host/operations.ndjson` | Append-only event stream for inspection |

### Required Integrity Invariants
- **No competing active selectors:** Only `active.json` determines the active release. Directory scanning is forbidden.
- **Staging never modifies selector:** Staging writes exclusively to `versions/.incoming-...` then renames to `versions/<id>`, setting `phase: staged` in `lifecycle.json`. `active.json` remains untouched.
- **Pending state cannot activate:** A candidate cannot be activated by `lifecycle.json` alone. Restart checks `active.committed_operation_id == operation.operation_id`; if absent, commit is void and precommit recovery applies.
- **Committed release cannot be rolled back by stale pending phase:** Once `active.json` is atomically replaced, restart recognizes the commit even if `lifecycle.json` still reflects `committing`.

## 6. Native Stage-Abandon Test and Evidence

- **Test Name:** `p6_gate_tests::stage_copy_failure_after_durable_intent_abandons_operation_and_leaves_selector_unchanged`
- **Location:** `lifecycle-host/src/p6_gate_tests.rs:333`
- **Method:** Real native Windows filesystem sharing violation: pre-creates `.incoming-{operation}/locked_file.bin` with `OpenOptions::share_mode(0)`.
- **Verified Flow:**
  ```text
  Engine A active
         |
         v
  Host persists stage intent (phase: staging in lifecycle.json)
         |
         v
  Copy fails with ERROR_SHARING_VIOLATION
         |
         v
  Host invokes abandon_stage(): removes incoming, marks PHASE_ABANDONED, logs engine_stage_abandoned
         |
         v
  Engine A remains committed (active.json byte-identical)
         |
         v
  Restart reconciliation returns StartPlan::Start (Engine A restarts)
         |
         v
  Successor valid stage (new operation) stages cleanly (phase: staged)
  ```
- **Assertions:**
  1. Stage intent was durably recorded prior to copy.
  2. Stage failed after intent write.
  3. Original Engine A remained committed.
  4. Active selector `active.json` was byte-identical.
  5. Incomplete package never reached `versions/`.
  6. Failed operation is terminal (`abandoned`) with failure diagnostics.
  7. Later stage of valid Engine succeeds.
  8. Host lifecycle is not wedged or blocked.
  9. Restart reconciliation safely restarts Engine A.
  10. Disk residue is inert and discarded.
- **Evidence:** `docs/reviews/evidence/2026-11-02-p6-g0-close-stage-abandon.json`

## 7. Precommit Engine B Diagnostic Logging Findings

An exhaustive tracing of Tauri process launch, child stderr redirection, and Node startup was performed:

1. **Initialization Path:**  
   `src-tauri/src/main.rs:493-517` constructs `<profile_root>/runtime/` and opens `<profile_root>/runtime/runner.log` as the child's `stderr`.
2. **First Possible Log Write:**  
   Any early stderr emitted by the Node runtime executable before or during `--p6-maintenance` argument processing.
3. **Preflight Maintenance Execution:**  
   In `--p6-maintenance`, `runtime/runner.mjs` executes `runP6MaintenancePreflight()` from `runtime/host/p6Maintenance.mjs`.
4. **Store Boundary Verification:**  
   Candidate B opens ONLY the disposable scratch database at `DESZO_P6_PREFLIGHT_STORE` (`.deszo-host/p6/<operationId>/preflight/state.sqlite`) using `new DatabaseSync(preflightStore, { readOnly: true })`. The production Store directory (`<profile_root>/store/`) is NEVER opened.
5. **No Mutation of Durable State:**  
   Logging writes exclusively to `runtime/runner.log`. SQLite files, journal tables, and Host lifecycle files are not touched by stderr logging.
6. **Failure Diagnostics Preservation:**  
   If candidate B crashes during preflight, `runtime/runner.log` retains the crash diagnostics on disk for operator inspection.
7. **No Readiness Impersonation:**  
   The Host never treats log file existence or content as readiness evidence. Preflight readiness is determined solely through authenticated IPC (`engine.maintenance_ready`) bound to PID, candidate generation, copy SHA-256, and Store integrity checks.

**Conclusion:** Precommit diagnostic logging satisfies all safety invariants without modification to production code.

## 14. Exact P6-BUILD Contract and Boundary

### 14.1 Host Operations Provided by G0
The Rust Lifecycle Host provides the following authenticated IPC endpoints:

```text
engine.stage(operationId, fromEngineBuildId, toEngineBuildId, packageSha256, shellBuildId, generation)
  -> { phase: "staged", ... }

engine.switch(operationId, fromEngineBuildId, toEngineBuildId, packageSha256, shellBuildId, generation)
  -> { accepted: true, ... }

engine.switch_status(operationId)
  -> { phase: string, failure?: string, preflight?: object, ... }

engine.maintenance_ready(operationId, pid, applicationPid, engineBuildId, shellBuildId, generation, copySha256, storeSchemaVersion, migrationCount, quickCheck)
  -> { ok: true }

engine.maintenance_wait(operationId)
  -> { decision: "pending" | "commit" }

custody.*
  -> Process Custody commands under the lifecycle capability
```

### 14.2 Host Invariants
1. Staging never writes `active.json`.
2. A switch requires an exact pre-existing staged package.
3. Custody starts are fenced, and zero active Custody Jobs are proven before stopping Engine A.
4. Candidate B runs dedicated read-only preflight against disposable copy before commit.
5. The live Store is never preflighted, never snapshot-restored, and never modified before commit.
6. Fallback to exact Engine A is permitted only precommit and only if production Store facts remain unchanged.
7. Atomic update of `.deszo-host/active.json` with `committedOperationId` is the single commit point.
8. Postcommit failures leave Engine B selected (no automatic postcommit rollback).
9. Legacy activation `lifecycle.activate_candidate` remains strictly refused (`p6_legacy_activation_refused`).

### 14.3 Responsibilities of P6-BUILD
P6-BUILD must implement:
1. Automatic trigger from an accepted, eligible `ProtectedSelfRepairHandoff/1`.
2. Exact source reconstruction from immutable P5 Store objects.
3. Source and Git identity verification.
4. Trusted installed builder invocation producing byte-reproducible packages.
5. Release package construction conforming to `build.json` schema 2.
6. Build provenance and `P6BuildReceipt/1` generation.
7. P5 candidate eligibility revalidation at the final pre-switch boundary.
8. Invocation of Host `engine.stage` then `engine.switch` via the internal trusted bridge.
9. Durable build outcome logging and diagnostic retention.
10. Autonomous P5 enrollment continuation without recurring Owner approvals.

### 14.4 Strict Prohibitions for P6-BUILD
- NO per-release Owner build approval.
- NO per-release Owner activation approval.
- NO Judge installation approval.
- NO automatic grant/revocation framework.
- NO Host Self-Repair or automatic Host update.
- NO general desktop updater service.
- NO automatic SQLite migrations.
- NO general Store rollback or snapshot restoration.
- NO second lifecycle supervisor or daemon.
- NO public exposure of the G0 manual switch HTTP test route in production packages.
