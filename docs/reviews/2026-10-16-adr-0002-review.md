# ADR-0002 review

Date: 2026-10-16  
Subject: [ADR-0002: Execution audit, supervised run control, and incident reporting](../adr/0002-execution-audit-and-supervised-control.md)  
Verdict: **Sound direction and accurate diagnosis; not ready to accept.** The audit and incident parts are well bounded. The supervision design has one decision that endangers its own acceptance scenario: the watchdog stops the run when the assistant falls silent. It also leaves three architecture choices open that determine whether per-run Stop and the emergency path can be built at all.

## Findings

### ADR2-01 (high): a silent assistant stops the run, which makes the primary scenario fragile

When the observation lease expires (proposed: 120 seconds without a semantic acknowledgement), the runtime closes dispatch and **stops the root run**, and the supervisor terminates the run's containment. The controller is a turn-based AI client such as Codex or Claude Code, so it acknowledges only while its model sits in a tool loop. Several ordinary events break that loop:

- the host ends the turn;
- the client compacts context;
- the model spends more than two minutes on one response;
- a host tool call times out;
- the user interrupts the chat to ask something.

Any of these stops a multi-hour shadcn/ui pilot and discards in-flight Agent and check work that consumed subscription quota.

The cost also grows with the run's length. At one acknowledgement per 120 seconds, the controller makes at least 30 tool calls an hour regardless of activity. A six-hour pilot therefore puts hundreds of health snapshots into the assistant's context. D21 asks for the assistant to *be able* to stop the run on a detected defect, not for a run to die when the assistant pauses. The ADR's stated goal ("must not leave work running unattended indefinitely") can be met more gently.

Recommendation:

- **Lease expiry first pauses dispatch.** No new Agent or check starts, in-flight work finishes or keeps running under its own timeouts, and an incident and UI notice are raised. Only a second, longer deadline stops the run, and the user can extend it from the window.
- **Deterministic runtime invariants stop at once**, independent of the assistant: capture failure, containment loss, scheduler or persistence errors. These already exist as "deterministic runtime invariants".
- **The acknowledgement deadline comes from measured host behavior.** Derive it from the Stage 5 matrix rather than fixing 120 seconds. Record each client's maximum unattended interval and compaction behavior.
- **Fit `watch_run` to host timeouts.** Its maximum wait (proposed 30 s) must stay below every client's MCP tool timeout (Codex: 60 s default), and the bridge's per-call HTTP timeout (currently 15 s) must exceed it.

### ADR2-02 (medium): per-run Job membership "before provider/check code executes" needs a decided launch mechanism

Node's `child_process.spawn` cannot create a suspended process, and the supervisor cannot assign a process Node starts until after it is already running. In that window the CLI can start descendants that escape the per-run Job; they stay in the app-wide Job only. The ADR defers this to "a reviewed native contract", but the choice changes the architecture. Option A or B is needed to meet the stated requirement; option C cannot meet it:

- **A. A native launch shim.** Node spawns a small supervisor-provided executable that creates the real CLI suspended inside the per-run Job, then resumes it and relays or inherits the stdio handles. Capture stays in Node.
- **B. The supervisor spawns provider and check processes** on the runtime's request and passes the pipes back. Spawning moves out of Node, which is a large change to the engine's process model.
- **C. Assign after spawn.** This leaves the escape window open.

Choose A or B in the ADR. State that nested Jobs (Windows 8 and later) are the mechanism, and that the per-run Job must be created as a child of the application Job. Say what non-Windows platforms do, or that supervised runs are Windows-only until specified.

### ADR2-03 (medium): headless runtimes have no supervisor, so they cannot offer supervised runs

Per-run containment, the native watchdog, the emergency control channel and the supervisor spool all assume the Tauri supervisor. Today Deszo also runs without one: `npm run runner`, the fixture runner, the smoke and pilot scripts, and `processContainment: 'standalone-best-effort'`. The ADR should state that a runtime without a native supervisor:

- refuses supervision grants with a typed error; or
- offers an explicitly degraded mode whose grant and audit record "no native watchdog, best-effort tree kill, no emergency channel".

It must never present such a run as supervised to the controller. The Stage 5 "stable installed controller" implies the first option for the pilot. Make that the rule.

### ADR2-04 (medium): the reasoning-display request must not change fingerprints or Context compatibility unintentionally

Requesting reasoning summaries changes provider invocation arguments: Codex `-c model_reasoning_summary=…`, Claude thinking display. Today's compatibility identities are built from those inputs:

- The Context binding `configurationHash` covers the provider, account, cwd identity, native configuration and `ADAPTER_VERSION` ([engine.mjs:1699](../../runtime/core/engine.mjs)).
- The M6 reviewer fingerprint includes the native profile.

If the new collector bumps `ADAPTER_VERSION`, or the display request joins the native profile, three things happen:

- every existing Context binding becomes incompatible and needs review;
- carried approvals and tasks are invalidated across specification revisions;
- an in-flight pilot's Contexts cannot continue after an upgrade.

Recommendation:

- Decide explicitly that reasoning *display* is an observation setting, recorded in the invocation manifest but excluded from `configurationHash` and reviewer and task fingerprints.
- Reasoning *effort*, which changes model behavior, stays included.
- Parser-only adapter changes must not bump the version that gates binding compatibility.
- Cover this in the Stage 1 compatibility fixtures.

### ADR2-05 (low): who may file and update incidents is unstated

The incident commands are "scoped HTTP/MCP commands", but the ADR does not say whether the ADR-0001 external token alone can create or update incidents, or only a supervision-grant holder can. The external authoring scope already covers any bridge, which includes clients misled by untrusted run output. Filing is low harm, but `update_incident` (triage status, "confirmed" cause) should not be writable by the same untrusted channel that reports suspicions. Add incident operations to the ADR-0001 scope matrix:

- creating or appending an incident is allowed under the external token or a grant;
- triage, confirmation and closure are first-party only;
- every write records the authenticated session.

### ADR2-06 (low): document precision

- **Header rendering.** The header lines (Date through Primary acceptance scenario) lack the two-space Markdown line breaks used in ADR-0001, so they render as one paragraph.
- **Placement of the 30 s and 120 s defaults.** They are "proposed" in prose, yet the acceptance text treats them as targets. Move both to the Stage 1 contract with the rule from ADR2-01, so the ADR's acceptance does not fix them.
- **Backpressure versus timeouts.** "Backpressure or stop execution" deserves one sentence on the interaction: pausing reads from a child's pipe stalls the child, and its own timeout may then fire. Spill to disk first, and apply backpressure only while the disk writer lags.

## Recommended path

Revise ADR2-01 (watchdog semantics), and decide ADR2-02 and ADR2-03 in the ADR text, because these determine what can be built and how the pilot behaves. ADR2-04 and ADR2-05 can be settled with contract rules in Stage 1. Keep the ADR **Proposed** until then. The documentation-only scope of the current request is respected: no application code or settings changed.
