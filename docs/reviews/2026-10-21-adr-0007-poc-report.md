# ADR-0007 PoC report: Codex App Server feasibility for event-driven Judge attention

- Date: 2026-10-21
- Subject: [ADR-0007](../adr/0007-event-driven-judge-attention-and-compact-evidence.md), amendments T01 and T02 from the [third review](2026-10-21-adr-0007-third-review.md)
- Evidence: [`evidence/2026-10-21-adr-0007-poc/`](evidence/2026-10-21-adr-0007-poc/README.md) (runner, sanitized results, README with reproduction steps)
- Status of this report: a recommendation. It does not accept ADR-0007, and it does not enable anything. The acceptance decision belongs to the user.

## 1. Executive summary

**Architecture: not ready for acceptance as written.** The third review's two findings are resolved in the ADR. T01 (serialized turns against the 30-second wake-up rule) is resolved by an amendment that uses a separate queue-wait bound. T02 (single-writer ownership of a dedicated session) is **not** resolved by the mechanism the ADR proposed. A separate `CODEX_HOME` does not make the session structurally single-writer. The PoC showed that a copy of the rollout file, or a move of a live owner's file, defeats the storage separation, and that a superseded owner that is still alive keeps writing. The Dedicated configuration therefore needs a different enforcement mechanism: custody by the protected worker principal, host-performed fencing, and clone detection. Custody is an architectural change and depends on ADR-0006's protected principal, which has not been verified for this purpose.

**Adapter feasibility: partly demonstrated.** The installed Codex App Server (0.163.0-alpha.10.2) creates, persists and resumes sessions in an isolated home without a sign-in, and it exposes a scoped MCP tool to a resumed session. It emits `turn/started` for an admitted turn, can bound an active turn with `turn/interrupt` in tens of milliseconds, and recovers an interrupted turn by identifier without starting a duplicate. These are the primitives the design needs.

**Real Judge wake-up: not demonstrated.** No sign-in exists in the isolated home, so no model answer and no scoped-tool call were obtained (POC-03, BLOCKED). The 30-second and 900-second deadlines were therefore never measured against a real model turn. All turn timings here are control-path measurements of turns that fail with HTTP 401.

**Recommendation: REQUEST ARCHITECTURAL CHANGES** (section 10). The narrow change is the Dedicated configuration's ownership mechanism (Amendment T02). T01 needs no architectural change.

## 6. Ownership and isolation findings

This section states precisely what the separated home does and does not guarantee.

**What a separate `CODEX_HOME` does.**
- Identifier-based discovery is separated. Another home lists nothing and cannot resume the session by identifier (POC-02, POC-05 S3b).
- The default profile's session store does not contain the dedicated session (POC-05 S4).
- Within one home, a second live writer is refused by a native per-thread writer lock (`thread-writer-locks/`). The lock files are zero-length and persist after exit, so their presence proves nothing about whether a lock is held. The refusal is the observable behaviour (POC-05 S1). The mechanism is presumed to be OS-level file locking; that was not verified.

**What it does not do.**
- It does not stop a process running as the same operating-system user from copying the rollout file. A copy in another home resumed as the same session identity and accepted writes while the owner was alive (POC-05 S3c).
- It does not stop a live owner from writing after its file has been moved. A move succeeded while the owner was alive, and the owner's next write landed in the moved file (POC-06).
- It does not know the owner generation. A superseded owner that is still alive keeps writing (POC-05 S2). The App Server has no concept that would let it refuse one.
- It does not make a session durable before its first write. A session created with no items was not resumable after a kill (POC-06).

**Conclusion.** With custody left to the user's own account, a dedicated session is not single-writer. The guarantee the ADR needs has to come from outside the App Server: the host must own the custody of the rollout and must fence the previous owner before any move. Those are the requirements in Amendment T02.

**Cloned sessions.** The ADR requires detecting cloned sessions. The PoC shows a clone is possible and accepted, but **no detection mechanism was tested**. The fingerprint check in T02 item 4 is a proposal.

## 7. Architecture gaps

Only gaps demonstrated by the experiments, or needed to interpret them, are listed. Each is classified.

| # | Gap | Class | Evidence |
| --- | --- | --- | --- |
| G1 | Storage separation is presented as isolation for the Dedicated configuration. Copies and moves by a same-user process defeat it. | **Architectural contradiction** | POC-05 S3c; POC-06 move |
| G2 | The App Server has no owner generation, and a superseded live owner keeps admitting turns. Fencing has to be host-performed by termination and admission checks. | **Architectural contradiction** (with the ADR's assumption of a single-writer guarantee) | POC-05 S2; POC-06 stale write |
| G3 | A second `turn/start` during an active turn is merged into it, with no separate lifecycle and no recorded item. Serialization must be adapter-side. | **Unsupported client behaviour** (the ADR assumed the server would not admit it) | POC-04 default arm |
| G4 | The native queue serializes correctly, but `thread/queue/*` and `thread/resume` by path require `experimentalApi`. Adopting it widens the protocol surface. | **Unsupported client capability** without review | POC-04 native-queue arm; POC-05 S3a |
| G5 | A session with no writes is not durable across a kill. The adapter must seed before reporting creation. | **Implementation defect** to avoid (not a design flaw) | POC-06 early kill; seeded PASS |
| G6 | Real turns need a signed-in isolated home. POC-03 and every provider-dependent claim are blocked on the user's device sign-in. | **Missing tooling / authorization** | POC-03 |
| G7 | The adapter-side queue, admission fence, clone detection and custody are not built. | **Implementation gap** | Not an experiment result |
| G8 | Custody needs the ADR-0006 protected principal to own the dedicated home. That is unverified and needs elevation to test. | **Architectural dependency** on ADR-0006 | Section 9 |
| G9 | Sandboxing of Codex's own tool execution was not examined. Turn tools were not exercised with a model. | **Unassessed** | Not tested |

No experiment shows that the *App Server* violates an ADR requirement it was never meant to enforce. The contradictions are with the ADR's assumptions about storage isolation and the single-writer guarantee.

## 8. Readiness assessment

Each is evaluated separately.

**Architecture acceptance: not ready.**
- T01: resolved in the record. Acceptable as amended, subject to the user's decision on the native queue (G4).
- T02: the Dedicated configuration's enforcement mechanism is not acceptable as written. It needs custody, host-performed fencing and clone detection, and custody depends on ADR-0006. This is a change to the architecture, and only the user can accept it.
- Interactive configuration: unchanged, unverified, and still dependent on client-supported exclusion (ADR-0007 section 3).

**Implementation readiness: low.**
- The adapter, the admission fence, the adapter-side queue, clone detection, custody and seeded creation are not built.
- The native bounded-command and protected-principal pieces of ADR-0006 that custody relies on are not verified for this purpose.
- The PoC harness is a disposable evidence tool. It is not production code and is not wired into Deszo.

**Operational enablement: not enabled, and not supported.**
- No configuration is enabled. The Dedicated configuration is unsupported for automatic enablement until custody is verified (T02 item 1). The Interactive configuration is unsupported until its exclusion is shown.
- A real Judge wake-up has not been demonstrated (POC-03 blocked). The 30-second deadline has not been measured against a model turn.

## 9. Recommended next steps

Ordered by technical dependency and risk. Each step needs its own authority where it is physical or costs money.

1. **Decide the Dedicated custody requirement** (user decision, architectural). Accept or reject T02 item 1: that the worker's protected principal, not the interactive user, owns the dedicated home. Until this is decided, no Dedicated configuration can be enabled. Rejecting it means the Dedicated configuration is withdrawn in favour of the Interactive configuration, whose exclusion must then be shown.
2. **Verify custody under the ADR-0006 principal** (requires elevated installation; human step). Create the dedicated home under the protected principal, deny the interactive user write access, and repeat POC-05 S3c and POC-06 as the user. Expected: the copy and the move are refused. This is the only test that can confirm or refute T02 item 1.
3. **Sign the isolated home in** (user action: `codex login --device-auth` with `CODEX_HOME` set to the isolated home, as in the README). Then rerun POC-03 and the turn arms of POC-04 and POC-06. This measures real wake-up, the scoped-tool call and the 30-second and queue deadlines against model turns, and it is the only way to resolve G6.
4. **Decide on `experimentalApi`** (G4). If the native queue is not wanted, keep the adapter queue. If it is, review the capability separately.
5. **Prototype the admission fence and clone detection** on the PoC harness: owner-generation and session-fingerprint checks before each `turn/start`, and detection of a copied rollout at the next admission. Each needs a negative test (a stale generation and a clone must both be refused).
6. **Recalibrate `queueWaitBoundMs`** from authenticated turn durations (step 3). Confirm or change the 600 s default before the first enablement.
7. **Only then** consider an adapter implementation in the existing ADR-0006 worker, following ADR-0007 section 7 steps 2 and 3.

## 10. Final verdict

**REQUEST ARCHITECTURAL CHANGES.**

The evidence refutes the ADR's claim that a separate `CODEX_HOME` makes the Dedicated configuration single-writer. The experiments show a same-user copy and a same-user move both defeat it, and that a superseded owner keeps writing. The ADR must therefore change its enforcement for the Dedicated configuration from storage isolation to host-owned custody with fencing and clone detection, and that change depends on the ADR-0006 principal. This is an architectural decision, and only the user can make it.

The third review's T01 is resolved by amendment without architectural change, and the adapter-side serialization it requires is demonstrated to be necessary.

This verdict is **not** a rejection of the Codex adapter. The primitives the design needs are present and behave as described in the schema: session persistence and resume, scoped tools after resume, turn-start events, bounded turns, and reconciliation after a kill. What is missing is a real model turn (POC-03) and an ownership mechanism that does not depend on the App Server. If the user rejects the custody requirement, the Dedicated configuration should be withdrawn, and the adapter should not be built on the storage-isolation assumption.

## Limitations of this PoC

- **No model answer was obtained.** Every turn ended in an unauthenticated 401 after Codex retried. Those requests were sent to the provider endpoint without credentials and were rejected. No charge is expected, and none was measured. This is disclosed because the isolated turns did reach the provider edge.
- **The default profile was not exercised live.** It was only checked by file names, to avoid altering the user's sessions.
- **Custody and clone detection are untested.** Their absence from the evidence is the reason they are recommendations.
- **Results are from one machine and one client version.** They are not claims about other Codex versions or about Deszo's own runtime environment.
- **The experimental queue and path resume were tested only with the capability declared.** Behaviour without it was not measured for the queue.
- **Unexplained process.** A full runtime test run (`node --test … runtime/tests/*.test.mjs`, parent `cmd.exe`, started 14:52 on 2026-10-21) was running in the repository during this work. It was not started by this task, and it was left running.
- **Authorization.** No Deszo grant, consent or budget was used. The PoC made no billable model call. The user's request for real turns was not satisfiable without a sign-in, so the turn experiments used only the unauthenticated path.
