# ADR-0008 and ADR-0009 second review

Date: 2026-10-22  
Subject: the rewritten [ADR-0008](../adr/0008-portable-ephemeral-lifecycle-host.md) and [ADR-0009](../adr/0009-workflow-native-judge-and-exclusive-external-input.md), revised after the [first review](2026-10-22-adr-0008-0009-review.md)  
Related evidence: [independent continuation verification](2026-10-22-workflow-continuation-independent-verification.md) (verdict PARTIAL)  
Verdict: **Both ADRs have changed materially, not just been amended.** ADR-0008 no longer has a time-bounded autonomy grant. It introduces a permanent Owner Token, and it now specifies the self-repair continuation that the independent verification found entirely unimplemented. Most first-review findings are resolved or deliberately decided. Neither ADR is ready to accept, because the rewrite introduced:

- a conflict with a still-confirmed requirement (D26);
- an undefined Owner Token scope that may remove ADR-0001's first-party/external separation;
- two factual errors about the current schema;
- several gaps in the continuation contract that the verification exposed.

## ADR-0008 findings

### ADR8-S01 (high): the permanent Owner Token conflicts with confirmed requirement D26 and removes every time bound on unattended self-modification

D26, which remains a confirmed requirement, asks for automatic approval "for a bounded period, for example twelve hours". ADR-0008 now has no time bound at all:

- the Owner Token is permanent until revoked;
- an accepted workflow needs no reauthorization;
- revocation explicitly does not stop running work.

An autonomous workflow with self-repair can therefore keep rebuilding and relaunching Deszo for as long as its node budgets allow. Only budgets and a manual Stop bound it.

That may be the user's new intent. If so, the register must say so:

- mark D26 superseded or revised by D30, with the user's decision;
- state in ADR-0008 that unattended duration is bounded only by workflow budgets and Stop.

If it is not the intent, keep a bound that does not need RAM leases: a per-workflow **absolute wall-clock deadline** captured at start, stored durably and enforced by the Engine like any other budget, which the ADR already relies on. Either way, the requirement and the design must stop contradicting each other.

### ADR8-S02 (high): define the Owner Token's scope against the ADR-0001 credential matrix

The Owner Token gives "full authorized MCP access" (§4.1), and §10 says it "aligns" with ADR-0001. ADR-0001's central boundary, however, is the split between the **external** scope, which can author and request runs, and the **first-party** scope, which can approve run requests, change settings, create workspaces, recover runs and use Context chat.

If "full" means first-party, any MCP client holding the Owner Token can do all of that. In particular, it can approve its own run requests and disable external-run confirmation, which removes the confirmation feature ADR-0001 was revised three times to make enforceable.

State explicitly which ADR-0001 routes the Owner Token authorizes, preferably the external scope plus answering questions. State also that first-party actions stay with the Deszo window, and that the Owner Token replaces, or coexists with, the per-runtime external token. Add that mapping to the route/credential matrix.

### ADR8-S03 (medium): the continuation contract lacks its trigger, its run linkage and the restart-survival rule

The independent verification established that none of §7's continuation steps exists in production. The ADR is now the contract for them, and it must specify the points the verification exposed:

1. **Who triggers Suspend.** "When a repairable Deszo defect or blocker is identified" names no actor. Under ADR-0009 only the Judge may escalate, so define a typed Judge outcome, for example `REQUEST_LINKED_REPAIR`, plus Engine invariant failures. The Engine then suspends the parent and creates the repair run. No other role or external caller may.
2. **Durable linkage.** A production record linking parent, repair, resume point and state, written atomically with the repair run's creation. Today no table or column links them.
3. **Restart survival.** `Engine.recover()` must keep a parent with an open link in `waiting_for_user`, and rebuild its in-memory run state, instead of converting it to `interrupted`. Otherwise `recoverRun` refuses it, as the strict test shows (409). State this as a required change, not an existing behavior.
4. **What the repair run is waiting for across the restart.** ADR-0008 §7 Step D says the new Engine "marks the linked repair workflow as completed". ADR-0009 §6 step 5 says the repair "completes its final node" after the restart. Pick one. The clean form is this: the Judge's `REQUEST_LIFECYCLE_ACTION` result is a committed outcome; the repair run then pauses durably as `waiting_for_user` / `lifecycle_pending`; after a `confirmed` Host receipt, the Engine finalizes the repair and resumes the parent through the existing `waiting_for_user:retry` transition.

### ADR8-S04 (medium): "zero redundant replay" across an Engine upgrade needs a compatibility rule

After a repair, the parent resumes in a **new Deszo version**. Today, reuse of completed outputs works by recomputing fingerprints (`reuseSource()`), and it rejects mismatched `EFFORT_POLICY_VERSION`, adapter or fingerprint composition. A repair that changes any of those, which is plausible for an Engine defect, would make the parent's completed nodes unreusable after the switch. They would then be re-run or refused, violating §7's "zero redundant replay".

Specify one of these:

- **Same-run resumption.** The parent resumes as the **same run**, from its own committed attempts, which is the restart-survival design in ADR8-S03. Fingerprint reuse is then not needed.
- **A compatibility gate.** Before activation, the contract tests prove that the candidate reproduces the persisted fingerprints of the suspended parent's completed nodes, and activation is refused otherwise.

### ADR8-S05 (low): make the contract-test harness concretely protected and recorded

§6.2 places the lifecycle contract tests "outside the candidate build's editable workspace". The Developer role, however, runs Full Access CLIs under the same account. Specify:

- that the harness ships with the Host installation, not the repository;
- that its version and digest are recorded in each activation receipt;
- that a harness that has changed since installation blocks activation.

This is a guard against accidental drift, consistent with the stated local threat model.

## ADR-0009 findings

### ADR9-S01 (medium): `runs` has no `pause_reason`; §5's "without schema migration" is wrong

§5 says the existing infrastructure works "without schema migration", and §11 maps external-input waits to `runs.pause_reason = 'external_input'`. The `runs` table has no `pause_reason` column. It exists only on `loop_executions` and `map_executions`, each with its own `CHECK` list. Migration 14 must add a run-level pause reason with an enumerated `CHECK`, covering at least `external_input`, `linked_repair`, `lifecycle_pending` and `stagnation_blocked`, and a typed reference column such as `pause_ref` for the question or link ID. Correct §5 accordingly.

### ADR9-S02 (medium): question persistence across a restart requires the same `recover()` change

ADR9-03 requires that the question persists across an application restart while the run waits. Today `recover()` turns every `waiting_for_user` run into `interrupted`, and the answer path depends on the run staying addressable. Under the same rule as ADR8-S03 item 3, state that runs waiting with reason `external_input` survive `recover()` unchanged and are rebuilt in memory. Add a restart to the ADR9-03/ADR9-04 scenario: question asked, Engine restarted, answer submitted, resumption without replay.

### ADR9-S03 (low): channel-neutral answers, so record the channel and keep high-consequence questions possible

Under the operator-neutrality decision, an MCP client holding the Owner Token can answer the Judge's question itself, including a question that decides a requirement or a lifecycle step. This is an accepted design choice. Two cheap safeguards keep it honest without classifying authorship:

- always record `responder_source`: the channel, plus the client identity where known. The proposed `workflow_answers` table already has the column;
- allow a saved question type to require the Deszo UI channel when the workflow author chooses. The default stays neutral.

## Recommendation

1. Resolve ADR8-S01 and ADR8-S02 with the user. They change what the user has authorized: an unbounded duration, and the Owner Token's scope relative to ADR-0001.
2. Add the continuation contract details: ADR8-S03 (trigger, linkage, `recover()` survival, repair pause point) and ADR8-S04 (compatibility rule).
3. Correct the schema statements in ADR9-S01 and ADR9-S02.

Both ADRs stay **Proposed**. When implementation starts, the strict continuation test (`runtime/tests/workflow-continuation-strict.test.mjs`) should be promoted from `todo` to required as ADR8-01's executable acceptance check.
