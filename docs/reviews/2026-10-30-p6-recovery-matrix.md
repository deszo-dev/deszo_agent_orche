# P6 Minimal Architecture — Recovery and Fault Matrix

Date: 2026-10-30. Design: [ADR-0010](../adr/0010-p6-trusted-build-activation-rollback.md), [contracts](2026-10-30-p6-contracts.md).  
This matrix maps the original P6-C01–C18 obligations to the simplified autonomous operation. It is a test plan, not passing P6 evidence.

H1 cannot meet the switching rows. It must refuse activation before stopping A. Only a separately deployed P6-capable Host may switch Engine releases.

## 1. Recovery rules

- P5 Store objects and the accepted handoff remain source authority. Branches, build output, Host status, and directory names do not replace them.
- Engine A owns pre-switch eligibility and build. The Rust Host owns exact release selection and process state after it accepts the fixed switch request.
- One nonterminal update per installation; one B launch and one A fallback launch per operation.
- The Host's existing installation-wide active-selection record is authoritative. Per-profile operation state and append-only Host audit are observations.
- Engine A must settle work to zero active Custody Jobs; Host then fences new starts and independently verifies zero before stopping A. Host never classifies or kills workflow/provider jobs.
- Host selects B only after its dedicated read-only preflight succeeds. Fallback to A is allowed only before B commit, with unchanged SQLite sidecars/Store inventory and certain process termination. Regular API startup occurs after commit; a failure there leaves B selected.
- Any changed/unknown process or Store state holds. No database snapshot, migration, external-effect replay, implicit new Repair, or candidate substitution.
- The Host operation records the immutable target before effects. Restart/replay resumes that operation or records a terminal hold; it never resets the B/fallback launch limits.

## 3. Coverage of required failures

| Required failure | Covered by | Recovery invariant |
|---|---|---|
| Engine dies during build / after build completion | C02–C04 | Same Custody invocation; receipt only from exact complete evidence |
| Incomplete staged release or candidate changed after verification | C05–C06 | Exact final rehash; A remains active |
| Engine dies after initiating switch; A fails to stop | C08–C10 | Durable fixed request; no B until all process trees are proved ended |
| Host crashes after stopping A or after recording B pending | C10–C11 | One Host selector decides; only exact B or exact A may start |
| B fails dedicated preflight after A stops | C12–C14 | Prove B tree ended and production Store unchanged; exact A fallback once, otherwise hold |
| B exits after A stops but before Host commit | C12–C14 | One A fallback only with unchanged post-shutdown Store and certain termination |
| B normal Engine/API startup fails after commit | C13–C14 | B remains selected; no unsafe automatic A fallback |
| Host crashes during fallback | C15 | One fallback identity/launch; uncertain state holds |
| B changes scratch SQLite/Store state before readiness | C14, C16, C17 | Production Store remains guarded; scratch is discarded; drift forbids A fallback or holds |
| Repeated Host restart and concurrent activation attempts | C11, C15, C18 | Host lock, one durable operation, stable launch limits |
| Parent Stop/P5 invalidation before final switch boundary | C08 | Latest eligibility is checked in A's final transaction |
| Two active Engines after uncertain termination | C09–C15 | Host never starts a replacement until all prior managed/Custody Jobs are proved ended |

## 4. Test layer and no-claim boundary

Unit and Store tests can prove exact handoff refs, operation uniqueness, P5 current eligibility, payload-only manifest file listing, and per-command replay. Rust Host tests must exercise process switching and crash recovery against real Windows Jobs and the zero-Custody fence. Installed Windows desktop E2E must prove the unchanged shell S loads Engine B from a separate root, the dedicated preflight runs before normal runner/Store/API side effects, all SQLite sidecar cases are read-only or fail closed, and the same P5 enrollment continues across at least two Engine updates. It must also prove a postcommit normal API failure leaves B selected.

A test plan is not proof. No P6 tests, Rust builds, Tauri builds, installations, or activations were run by this architecture revision. H1's current behavior remains the baseline until the separately authorized compatibility patch is implemented and verified.
