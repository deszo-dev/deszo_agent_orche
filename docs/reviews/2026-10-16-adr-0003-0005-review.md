## ADR-0003 findings

### ADR3-R01 (high): nothing independent catches an underestimated assessment

Plan selection is deterministic from the Analyst's assessment, and the risk floors in §3 apply only when the assessment *reports* the risky property. The case that hurts is the Analyst rating a change "local, clear criteria, limited consequences" when it actually touches persistence, process control or a shared contract. The compact rule then removes intermediate reviews and Map decomposition, and nothing outside the Analyst's own judgement questions it. The fixtures in Stage 3 ("deliberately underestimated critical changes") need a mechanism to test, and the ADR does not yet define one.

Recommendation, in two parts:

- **Deterministic source-derived floors.** These are policy rules over captured facts that the Analyst cannot lower. Examples:
  - touched paths that match declared critical areas (migrations, auth, process containment, persistence);
  - changed public interfaces or schemas;
  - dependency-graph fan-out above a threshold.

  The plan records both the Analyst's classification and the derived floor, and the stricter one wins.
- **Assessment review whenever a plan drops reference stages.** If the selected plan omits any stage of the reference workflow, the readiness reviewers, or one of them, must confirm the assessment's scope and risk grounds before implementation. Their confirmation joins the captured plan inputs.

### ADR3-R02 (medium): the assessment-to-workflow lifecycle is under-specified

The assessment precedes the workflow it selects, so it must run outside that workflow, yet the ADR also requires its work to be counted in the plan's aggregate budget. Specify:

- **Where the assessment runs:** as a run of a fixed, versioned assessment workflow, or as an external-client artifact with recorded provenance.
- **Who compiles the plan:** the runtime compiles plan plus templates into workflow JSON. Saving that JSON must go through ADR-0001's v3 conditional save with an ETag, since no client is meant to compile workflows itself.
- **How the runs are linked:** assessment run, plan revision and execution run, so that preparation accounting and reassessment revisions resolve deterministically.

### ADR3-R03 (low): the cost of the evaluation corpus should be stated before authorization

Seven case classes, repeated runs per policy variant, real providers, and one change at a time add up to a substantial number of subscription-quota runs. Stage 4 already requires separate authorization. Add a planning estimate (cases × repeats × variants × typical invocations) so the user can authorize it knowingly, and say which comparisons run first if the quota is limited.

## ADR-0004 findings

### ADR4-R01 (medium): mid-invocation context requests have no current mechanism

§4 proposes a typed intermediate context request that the runtime resolves and materializes, with a bounded turn and read budget. Managed Agents are one-shot CLI invocations (`exec` / `-p` / `--print`) with no channel back into Deszo during the call. ADR-0001 also deliberately keeps the management MCP bridge out of managed invocations. Two designs are possible, and they differ in consequence:

- **Request as the result, then resume.** The Agent ends its invocation with a structured "context needed" result. The runtime resolves it and continues the same native session with the added material. This needs a continued Context, which conflicts with ADR-0003's fresh-Context reviewers unless the fresh Context is defined to start at the first review turn of that step.
- **A separate read-only context MCP server for managed runs.** It must have its own isolation story, distinct from the management bridge: read-only, scoped to the package, and authenticated per invocation. The marker and preflight rules of ADR-0001 must then distinguish the two servers.

Pick one, or state the first as the initial mechanism, and say how its turns count against the aggregate budget.

### ADR4-R02 (medium): package selection must be deterministic, and adopting it will invalidate carried approvals once

Package semantic fingerprints are to participate in task and reviewer compatibility. Two consequences need stating:

- **Determinism.** The selector must give the same semantic package for the same captured inputs, by the same standard ADR-0003 sets for plan selection: stable ordering, no live reads. Otherwise carry decisions flap between identical runs.
- **One-time invalidation.** Adding the package fingerprint, plus the style and glossary versions, to reviewer and task fingerprints changes every existing fingerprint. Approvals carried under revisions-v1 become stale the first time packages are enabled. Either version the fingerprint so old records keep their meaning until a new revision, or state the one-time invalidation explicitly as a migration consequence.

### ADR4-R03 (low): REVIEW_INCOMPLETE needs a loop-level rule

An incomplete review supplies no approval, so a Gate requiring that slot cannot open. Inside the existing Specification or Delivery Loop, say what the loop does:

- retry with a widened package within the aggregate budget;
- after that, the loop pauses for the user, using the existing `waiting_for_user` path, rather than consuming iterations as if the review had been `CHANGES_REQUESTED`.

Otherwise implementations will treat it as a failed iteration.

## ADR-0005 findings

### ADR5-R01 (medium): choose the delivery checkout model

"A separate runtime-owned delivery checkout/worktree" leaves open two models with different safety properties:

- **`git worktree`.** It shares the caller's object store, refs and hooks, and writes worktree metadata into the caller's `.git`. It cannot check out a branch that is already checked out in the caller's tree; the precondition must then fail clearly. Cleanup must run `git worktree remove` or `prune`, and the hooks are the user's repository hooks, running under Full Access.
- **A separate clone** (`--shared` or `--reference`), followed by a final `git fetch` or ref update into the caller's repository under the expected-old-value condition. This touches the caller's repository only at the final ref update, and hooks are explicit.

The choice determines the locking, hook, cleanup and recovery contracts in §§2, 5 and 6, so decide it in the ADR. The second model fits "the caller's working tree and index remain untouched" more naturally.

### ADR5-R02 (low): delivery work should count toward ADR-0003's aggregate budget

The input contract has its own "execution/attempt limits". State that delivery attempts, environment smoke and reconciliation count toward the plan's aggregate attempt and time bounds from ADR-0003. Otherwise a delivery repair cycle becomes an unbounded second loop.

### ADR5-R03 (low): the pilot's named branch already has unrelated history

The [pilot brief](../pilots/shadcn-ui-brief.md) names `codex/shadcn-ui` as the destination of the accepted candidate. That branch now exists on origin and carries the ADR-0002 implementation commit. Under ADR-0005 rules, the pilot's delivery would have to advance an existing branch under an expected-ref condition, on top of unrelated infrastructure. Before the pilot, either:

- re-point the brief to a fresh branch from `main`, recording the absence condition; or
- explicitly accept the existing head as the captured base.

## Cross-ADR notes

- The three ADRs share consistent vocabulary: candidate versus branch boundary, the criterion-to-evidence record, aggregate budgets, explicit bindings with no substitution, and audit gaps as unknown, never zero. The dependency direction is acyclic: 0003 plans, 0004 defines evidence and context, 0005 delivers.
- Each correctly limits the current request to documentation and requires separate authorization for implementation and real-provider runs.

## Recommendation

Revise the ADRs for ADR3-R01, ADR4-R01 and ADR5-R01, which are design decisions. Settle ADR3-R02, ADR4-R02 and the low findings in the ADR text or the Stage 1 contracts. Keep all three **Proposed** until then.
