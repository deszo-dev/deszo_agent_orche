# ADR-0001 to ADR-0004, ADR-0008 and ADR-0009: review of the 2026-10-23 amendments

Date: 2026-10-23  
Subject: [ADR-0001](../adr/0001-external-workflow-authoring-api-and-mcp.md), [ADR-0002](../adr/0002-execution-audit-and-supervised-control.md), [ADR-0003](../adr/0003-task-assessment-and-workflow-planning.md), [ADR-0004](../adr/0004-agent-communication-and-context-contracts.md), [ADR-0008](../adr/0008-portable-ephemeral-lifecycle-host.md) and [ADR-0009](../adr/0009-workflow-native-judge-and-exclusive-external-input.md) as edited on 2026-10-23 at 17:52, together with the [decision register](../DECISIONS.md) and the [ADR index](../adr/README.md)  
Earlier reviews: [ADR-0008/0009 second review](2026-10-22-adr-0008-0009-second-review.md), [Revision 3 review](2026-10-23-progress-driven-execution-revision-3-review.md), [universal monitoring review](2026-10-23-universal-agent-monitoring-and-decision-authority-review.md)  
Verdict: **The accepted bodies of ADR-0001 to ADR-0004 are unchanged and remain sound. None of the new amendments is ready to adopt, and ADR-0008 and ADR-0009 stay Proposed.**

What improved:

- ADR-0009 now states the actual m14 contents and that `runs.pause_reason` does not exist.
- ADR-0008 cites Proof B and limits its claim to termination, not preservation of a live CLI.
- A new protected System Self-Repair amendment removes the risk that ordinary authoring defines the lifecycle-authorizing workflow. It does this through an installation-owned manifest and a first-party update path.

Four high findings remain:

- The D26/D30 conflict is still undecided (AMD-01).
- Who may grant more automatic-decision capacity, and the Owner Token's scope, are both still undefined (AMD-02).
- The new Publication amendment would break today's save-then-run flow for every v3 client (AMD-03).
- `PROGRESS_UNVERIFIED` is now written into ADR-0002's amendment unchanged (AMD-04).

## High findings

### AMD-01 (high, carried from ADR8-S01): D26 versus D30 is still undecided, and the conflict is not limited to new policies

The register now says the conflict "must be decided before adopting a new unattended or deadline-free policy". However, ADR-0008's core authorization model already contradicts D26, which is still a confirmed requirement ("a bounded period, for example twelve hours"). That model is:

- a permanent Owner Token;
- no reauthorization of running workflows;
- revocation that does not stop running work.

ADR-0008 cannot be accepted as written until the user makes one of two choices:

- record that D30 supersedes D26; or
- keep a durable per-workflow wall-clock bound.

This is a user decision, not a documentation fix.

### AMD-02 (high, carried from UAM-R02 and ADR8-S02): "an authorized external decision" can be an automated client

ADR-0003's amendment says "Only an authorized external decision can add capacity". ADR-0009's amendment lists "a specified additional allowance" among the owner's options. ADR-0008 §4.1 still gives the Owner Token "full authorized MCP access", and ADR9-10 applies UI and MCP answers identically. The repository ships an external AI controller (`skills/deszo-control`).

An MCP client holding the Owner Token can therefore grant allowances repeatedly, or start a new top-level run, which opens a new lineage. The "finite automatic decisions" guarantee does not hold against that.

Required change:

- **Who may grant capacity.** Capacity grants need first-party authority. Alternatively, MCP-originated grants count against an owner-set ceiling that no MCP request can raise.
- **What a lineage is.** Lineage identity covers `run_links`, ADR-0003 plan revisions and restarts.
- **The Owner Token's routes.** Map the Owner Token onto ADR-0001's external and first-party route matrix.

### AMD-03 (high, new): the Publication amendment breaks the v3 save-then-run flow unless a compatibility rule is defined

Today a run request targets a `kind='user'` workflow and must pin the **current saved** snapshot digest. `engine.mjs` refuses a mismatch with "The saved workflow changed; reload it before running". Every MCP client works this way: save, then request a run with the returned digest.

The amendment changes this. After migration, a save produces a Draft, and "only an immutable Published version may be selected for a new Run". A v3 client that saves an edit and then requests a run would pin a Draft's digest and be refused. Making v3 save publish implicitly would change the save endpoint's meaning, which the amendment explicitly forbids. The amendment defines the legacy migration and the mapping of pending requests, but not this flow, which is the common one.

Define the v3 compatibility rule before adoption. One rule that preserves today's observable behavior:

- under v3, saving a **valid** definition also creates a Published version atomically, matching today's rule that only valid saved definitions can run;
- an invalid v3 save creates only a Draft;
- a v3 run request resolves its pinned digest to the Published version with that digest.

Add an acceptance case that drives an unchanged v3 client through save, edit, save and run.

### AMD-04 (high, carried from UAM-R01): `PROGRESS_UNVERIFIED` will fire on most long healthy invocations

ADR-0002's amendment says: "an observable invocation without verified progress becomes `PROGRESS_UNVERIFIED`". After two checks it records an incident and routes it by policy. Task criteria are normally checked only **after** an invocation ends. Unless an adapter reports verified progress mid-invocation, every invocation longer than the diagnostic window therefore:

- produces an ADR-0002 incident; and
- where policy routes it, starts an AI review charged to a counter that is never refunded.

Required change:

- Define in-invocation progress evidence per adapter. Where none exists, report `insufficient_evidence`, with no incident and no AI review by default.
- Escalate only on stronger signals: no activity for the window, or a positive interaction or throttling signal.
- Relate the diagnostic window to the applicable deadline.

## Medium findings

### AMD-05 (medium): define how stagnation episodes compose with lineage allowances

ADR-0009's amendment keeps a finite allowance **per stagnation episode** and lets "objective progress against criteria fixed before the action" begin a new episode. It says these limits "compose with the root-lineage allowances". ADR-0003's amendment charges `automaticInterventionsUsed` for actions taken "after escalation", which is diagnostic escalation.

If an `AUTHORIZE_NEXT_ACTION` admitted after a stagnation episode is not charged to a lineage counter, the episode-reset loophole (PDE-R01) returns as soon as Stage 1B omits the aggregate caps. State two rules:

- every Engine-issued grant, whether from stagnation or from diagnosis, charges `automaticInterventionsUsed`;
- every Judge turn routed by the stagnation barrier charges a named counter.

Add the single accounting table requested in UAM-R08, covering ADR-0003's aggregate bounds, ADR-0009's Judge review budget, the episode allowance and the two lineage counters.

### AMD-06 (medium): map the final Self-Repair review onto the Judge's lifecycle proposal

ADR-0008's amendment introduces a mandatory final AI review with outcomes `APPROVE_REBUILD`, `REQUEST_CHANGES`, `REJECT_REBUILD` and `INSUFFICIENT_EVIDENCE`. It says a positive review "can authorize local rebuilding but never by itself grants activation".

The current contract, and the implementation, activate through the designated Judge's `REQUEST_LIFECYCLE_ACTION` (A8-I01, §5.2, and the `lifecycle_operations` intent). The amendment leaves three things open:

- whether the final reviewer is the designated Judge;
- whether one result carries both the verdict and the proposal;
- what `APPROVE_REBUILD` approves, given that the candidate has already been built when the final review runs.

Name the outcome by its effect, for example `APPROVE_ACTIVATION`. Require the Judge's lifecycle proposal to cite a favorable final verdict bound to the same branch, commit and candidate digest.

### AMD-07 (medium): the Host should run, or authenticate, the protected suite

The amendment places the harness in an installation-owned manifest, and says the Host "independently verifies its typed authorization and manifest". It does not say who **executes** the protected suite, or whether the Host verifies the suite's receipt. If the Engine runs it, the Engine is reporting on code that is replacing itself. The Host is the one component self-repair cannot replace (ADR8-10), and Proof B already has it verify the candidate's digest and manifest.

Have the Host launch the protected suite against the candidate, or verify a receipt that only a Host-launched harness can produce, before activation.

### AMD-08 (medium): §7 of ADR-0008 still describes a design the implementation replaced, and the code inverts the amendment's trust rule

**The text.** §7 is unchanged:

- the trigger is unspecified ("when a repairable Deszo defect or blocker is identified");
- Step A records a typed reason `linked_repair` that cannot be stored;
- Step D says the Engine "marks the linked repair workflow as completed".

What is actually implemented, and consistent with ADR-0009 §6:

- the link is created through the first-party `POST /api/v2/runs/:id/linked-repair` route;
- linkage is recorded in `run_links`;
- `recover()` holds the linked runs;
- the repair waits at a lifecycle gate until the Host receipt, then runs its final node;
- the parent resumes **in place** as the same run.

Update §7 to match.

**The code.** `linkedRepair.mjs` accepts any `kind='user'` workflow as the repair workflow, so ordinary authoring authority defines the repair workflow and its Judge. The amendment requires the opposite: a fixed, protected `kind='system'` definition. Record this as a required implementation change, alongside the still-unfixed check that compares workspace IDs only (PDE-R10).

### AMD-09 (medium, carried from UAM-R03): the arbiter boundary contradicts accepted ADR-0004 §3

ADR-0004's amendment says the restriction "applies to context assembly, artifact reads, tools and indirect agent transfers", and that the guarantee covers what Deszo "supplies and permits". Accepted ADR-0004 §3 states: "Context selection is not a filesystem sandbox. Full Access agents can have access beyond the selected package." Every adapter launches with approvals and sandboxing bypassed in the workspace `cwd`.

Choose one:

- require a verified, per-provider restricted-invocation capability for the arbiter, and for diagnostic reviewers that run while a Developer CLI is alive (ADR-0002 amendment), refusing providers that cannot be restricted; or
- limit the guarantee to information Deszo **supplies**, and drop "permits".

### AMD-10 (medium, carried from PDE-R04 to R07): the Custody text in ADR-0002 still lacks four PoC criteria

The Custody contract is now written in accepted ADR-0002's amendment and serves as the PoC's contract. It still omits:

- **Job topology.** Windows cannot transfer a running process into a different Job, so only invocations that Custody launches itself are eligible.
- **A Host crash.** The CLI must die with the Host (kill-on-close); otherwise it runs with nothing enforcing its limits.
- **A dedicated permit credential.** It must be separate from the lifecycle-receipt capability, bound to the Engine generation, and absent from every provider environment.
- **The steady-state capture path.** The spool import is the live stream path during normal operation, not only after a restart.

It also omits ADR-0002's supervised escalation and emergency Stop for CLIs that Custody owns. Its list of what Custody enforces names Stop, deadlines and the aggregate elapsed cap only.

## Low findings

### AMD-11 (low): ADR-0008's header mislabels Proof A

The header links "Proof A" to the [engine-native continuation report](2026-10-22-engine-native-continuation-implementation.md). The [Rust Host report](2026-10-22-rust-host-lifecycle-integration.md) and Proof B both use "Proof A" for Host → Node runner → Engine. Cite three things separately: the continuation proof, Host Proof A and Proof B.

### AMD-12 (low): Publication details

- **Conditional publish.** Publication should name the Draft revision it publishes (`If-Match`), so that a concurrent edit cannot be published unseen.
- **Which digest.** State whether the Published digest covers the layout (`view`). The existing `executionHash` excludes it; the snapshot digest includes it.
- **What a Run captures.** A Run captures current settings separately (`settingsArtifact`). State what Publication fixes and what is captured only at Run.
- **Editor events.** Add publication events to the `workflow_changes` feed used for editor synchronization.
- **System definitions.** ADR-0009's amendment says authority is "captured in the Published workflow version". It must also cover the protected system Self-Repair definition, which ADR-0001 says Publication does not make trusted.

### AMD-13 (low): register and index housekeeping

- `DECISIONS.md` still reads "Version 0.21, Updated 2026-10-22", although it has 2026-10-23 entries.
- `docs/README.md` reads "Version 0.29, Updated 2026-10-21" and has no change-log rows for 2026-10-22 or 2026-10-23.
- The register says "P21/P23/P25 clarifications" are recorded in ADR-0001, ADR-0008 and ADR-0009. None of them mentions P21 (immutable TaskResults) or P25, and no clarification of P23 is identifiable. Name the clarifications, or remove the claim.
- The A01–A13 IDs are not used in any ADR section (UAM-R13).

### AMD-14 (low, carried from ADR9-S03): keep `responder_source`

The previous §11 listed `workflow_answers.responder_source`; the corrected §11 names no answer fields. Keep the column in the future migration, and record the channel of capacity grants too, because AMD-02 depends on it.

### AMD-15 (low, carried): residual items from the universal monitoring review

- UAM-R04: add a provider-throttled classification, and forbid any AI decision from answering a CLI's interactive or permission prompt. Today stdin is closed after the prompt (`processes.mjs`), so `INTERACTION_REQUIRED` has no adapter basis.
- UAM-R05: enumerate the closed automatic action set, including whether an admitted action may stop a live invocation.
- UAM-R11: let the plan compiler size the lineage allowances.
- UAM-R12: state whether checks, builds and smoke tests are monitored.

## Recommendation

1. **The user decides** D26 versus D30 and the Owner Token's scope (AMD-01, AMD-02). Both ADR-0008 and the finiteness of every amendment depend on them.
2. **Before the Publication amendment is adopted**, specify the v3 compatibility rule and its client test (AMD-03).
3. **Revise the health trigger and budget composition** (AMD-04, AMD-05) in the ADR-0002, ADR-0003 and ADR-0009 amendments together, because they define one mechanism.
4. **Bring ADR-0008 §7 up to date** with the implemented continuation, and record the two implementation changes the amendment implies: a protected system repair workflow, and workspace isolation by physical path (AMD-08).
5. **Settle the Self-Repair activation chain**: final verdict → Judge proposal → protected suite run by the Host → Host activation (AMD-06, AMD-07).

No ADR, register entry, code or test was changed by this review.
