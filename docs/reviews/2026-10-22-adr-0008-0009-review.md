# ADR-0008 and ADR-0009 review

Date: 2026-10-22  
Subjects:

- [ADR-0008: Portable ephemeral lifecycle host (Rust + Dioxus)](../adr/0008-portable-ephemeral-lifecycle-host.md)
- [ADR-0009: Workflow-native Judge and exclusive external input](../adr/0009-workflow-native-judge-and-exclusive-external-input.md)

Verdict: **Both are clear, deliberate simplifications. Each states its weaker threat model honestly and keeps durable workflow state separate from ephemeral authority.**

- **ADR-0008 is not ready to accept.** It reintroduces the problem ADR-0006 was revised to fix: the candidate Engine, the code being autonomously rebuilt, is what enforces the Host's expiry and revocation. Self-modification is not "malicious same-user code", so the weaker threat model does not cover it. ADR-0008 also does not justify a second desktop UI stack.
- **ADR-0009 is close.** It needs a defined mechanism for distinguishing an actual human answer from an MCP client's own text. It should also reuse the existing `waiting_for_user` state rather than add `waiting_for_input`.
- **Neither is registered.** Neither ADR appears in the decision register or the ADR index yet.

## ADR-0008 findings

### ADR8-R01 (high): the self-modified Engine enforces the Host's grant, so expiry and revocation depend on candidate code

Under ADR-0008, the grant lives in Host RAM, and "Engine must enforce its own fail-closed admission behavior upon lost/expired grant" (§4.2, A8-I07, ADR8-03). The Engine, however, is the Deszo application the session repairs, rebuilds and activates. A candidate whose admission gate has a defect simply keeps dispatching after the grant has expired or been revoked. That candidate need not be malicious; it can be an ordinary bug introduced by the Developer role in `supervision.mjs`, the run-request path or the lease check.

The ADR's accepted limitation concerns "malicious programs running with equivalent user privileges". It does not cover the system weakening its own enforcement through normal autonomous work, which is the central use case. ADR6-R01 raised exactly this point. ADR-0006 answered it with host-side enforcement, and ADR-0008 drops that answer without replacing it.

Recommendation: let the Host enforce what it can enforce portably, and gate what it cannot.

- **Process-level enforcement.** The Host launched the controlling Deszo process. On expiry, revocation or Host-initiated Stop, the Host stops that process, so it does not have to trust the candidate to stop itself. Then expiry is enforced without the candidate's cooperation, using only the portable process APIs §6 already assumes. Make "on grant end, Host terminates the controlled generation (after a bounded graceful quiesce request)" an invariant. On Windows, the ADR-0002 application Job then takes down that generation's descendants.
- **Authority-code gating.** Activating a candidate whose changes touch the Engine's admission, lease, grant, run-request or containment code requires a fresh user decision in the Host UI, as ADR-0006 §4 required. Use ADR-0003's project-declared critical areas for Deszo to decide which changes qualify.
- **State the residual.** Between activation and the next grant check, a candidate's own gating is trusted. Only Host-side process termination and the activation gate bound that.

### ADR8-R02 (medium): credential custody when the Host is the launcher

Under the ADR-0001 custody rule, whichever process launches the runtime receives the first-party token on its private stdout. If the Host launches Deszo, the Host therefore holds full first-party authority (settings, workspaces, approvals, the confirmation toggle), which is far broader than its lifecycle policy. ADR6-R02 raised the same point. ADR-0008 §4.3 defines a new loopback secret but does not say what happens to the existing first-party token.

Specify one of these:

- **The Host launches the Tauri application,** whose supervisor keeps the first-party token. The Host receives only its lifecycle secret.
- **The Host deliberately holds first-party scope.** If so, state it as part of the accepted weaker threat model, including that a Host compromise equals full Deszo authority.

### ADR8-R03 (medium): justify Dioxus rather than reusing Tauri

The repository already ships a Rust + Tauri desktop application (WebView2 on Windows) with a React UI, a Rust supervisor and native tests. ADR-0008 adds a second Rust desktop UI framework, which also depends on a webview, for the Host's small consent and status surface. That doubles the UI toolchain, packaging, update and accessibility work. The rejected alternatives do not list "build the Host as a minimal Tauri application, or a separate Tauri binary sharing the existing build". Add that alternative with a reason, or choose it. If the reason is that the Host must not depend on the candidate's UI stack, a separate Tauri binary with its own frontend already satisfies that.

### ADR8-R04 (low): name the store lock as the competing-generation guard

§5.2 step 4 requires "confirms old Deszo application termination before starting a competing controlling generation". Portable APIs only observe the direct child process. Off Windows, a killed Tauri process can leave its Node runtime running. The real mutual exclusion already exists: `runner.lock` on the store root. State that activation requires the new generation to acquire the store's runtime lock, and that a lock held by an unknown process is `reconciling`, never forced. That gives a portable, testable guard instead of relying on process-tree observation.

### ADR8-R05 (low): monotonic clock freezes during sleep/suspend on Windows and Linux

§4.2 bounds duration within the Host process using a monotonic clock, but leaves suspend reconciliation open in §11. In Rust, `std::time::Instant` uses `QueryPerformanceCounter` on Windows and `CLOCK_MONOTONIC` on Linux, neither of which advances during system standby/sleep. A 12-hour session closed on a laptop for a weekend could resume with nearly 12 hours of apparent lease remaining. Specify that Host uses suspend-aware time (`GetTickCount64` / wall-clock sanity checks on Windows, `CLOCK_BOOTTIME` on Linux, `mach_continuous_time` on macOS) and conservatively expires the grant if elapsed wall-clock exceeds the absolute deadline.

## ADR-0009 findings

### ADR9-R01 (medium): "an authenticated human answer" needs a defined mechanism

`submit_human_answer` "must distinguish operator approval from text generated by Codex" (§6), and ADR9-07 refuses "nonhuman-forged" responses. The MCP write path, however, is called by the Codex **model**. A helpful or prompt-injected Codex chat can answer a question itself, and through ADR-0001's external token that call is indistinguishable from the user asking Codex to send the answer. The ADR defines no mechanism, so the criterion cannot be tested.

Recommendation: record the answer's provenance honestly, and let policy require a stronger channel where it matters.

- An MCP-submitted answer is recorded as an `operator_client` answer: client identity and session, not a verified human. It is acceptable for routine clarifications.
- The question schema declares a required answer channel. Questions that widen scope, accept a requirement interpretation with acceptance consequences, or approve a lifecycle step require an answer through the Deszo UI (first-party) or the ADR-0008 Host UI.
- The bridge marks `submit_human_answer` as requiring host-client tool approval, so the Codex user sees and confirms the call. That is a supporting layer, not proof.

### ADR9-R02 (medium): reuse `waiting_for_user`; do not add `waiting_for_input`

The engine's existing reachable pause state is `waiting_for_user` (M2 contract, 12 uses in `engine.mjs`), already used for recovery pauses and by ADR-0007's deadline outcomes. A second near-synonym run state requires a run-state migration and duplicates the recovery, Stop and Replay handling. §7 itself says to verify the existing vocabulary.

Model the Judge question as `waiting_for_user` with a typed pause reason (`external_question`) and a reference to the pending question record. Keep `blocked`/`reconciling` as outcomes for uncertain effects, as ADR-0005/0006 already do.

### ADR9-R03 (medium): add a deterministic route to the human that does not depend on the Judge

ADR-0007's review added engine-side `no_progress` triggers so that a Watcher that never escalates still reaches the Judge. ADR-0009 keeps those triggers, but routes them to the Judge, and only the Judge can reach the human. The same failure mode therefore moves one level up. A Judge that keeps returning `REVISE` or `APPROVE_REVIEW` without asking, whether weak, mis-prompted or injected, means the user learns of trouble only at final delivery or budget exhaustion.

The ADR already allows Engine-surfaced informational notices for hard failures. Extend that explicitly so the user is told without granting any role question authority, when:

- Judge visits for the same subject reach a configured bound without progress;
- the Judge revises the same candidate repeatedly;
- a declared fraction of the root budget is consumed.

These are system notices, not semantic questions. Add a negative test: a Judge fixture that never asks must still produce the user notice at the bound.

### ADR9-R04 (low): the Judge's lifecycle proposals inherit ADR8-R01

The Judge "may propose a typed `application.restart`/`application.activate_candidate`" (§9), and the Host executes it within the live grant. An autonomous model can thus activate a self-built Deszo. That is the intended capability. The authority-code activation gate from ADR8-R01 must apply to Judge proposals as well, and ADR9-08 should state that a Judge `APPROVE` never satisfies that gate.

### ADR9-R05 (low): attempt budget accounting during question resumption

§5.3 states that an answer may be consumed by another model turn when the Judge node is revisited. A node typically has a bounded attempt budget (e.g. 2 attempts). If asking a question consumes attempt 1, and evaluating the answer consumes attempt 2, the node exhausts its retry allowance before any normal failure recovery. Specify whether answer evaluation counts as a continuation turn or uses a distinct response-evaluation allowance so that legitimate questions do not trigger unintended terminal budget exhaustion.

## Shared finding

### ADR89-R06 (low): register both proposals and index them

Both ADRs defer register and index updates until acceptance, but earlier proposals (ADR-0006, ADR-0007) were registered as D/P items and indexed while still Proposed. That is the established practice, and it keeps the index from silently omitting live proposals. Add:

- the D items (requirements) and P items (proposals) for ADR-0008 and ADR-0009;
- the ADR index rows with status Proposed and the conditional "supersedes" notes;
- a note in the ADR-0006 and ADR-0007 entries that a superseding proposal exists.

## Recommendation

- **ADR-0008:** decide ADR8-R01 (Host-side termination on grant end, and the authority-code activation gate), ADR8-R02 (token custody) and ADR8-R03 (Dioxus versus Tauri). Then present it for acceptance together with its explicit threat-model tradeoff.
- **ADR-0009:** settle ADR9-R01 to ADR9-R03. ADR9-R04 follows from ADR8-R01.
- **Both:** register and index them (ADR89-R06). Keep them **Proposed**. ADR-0006 and ADR-0007 keep their current status until the superseding decisions are recorded, as both ADRs already state.
