# ADR-0001 to ADR-0004, ADR-0008 and ADR-0009: second review of the 2026-10-23 amendments

Date: 2026-10-23 (20:45)  
Subject: the six ADRs, the [decision register](../DECISIONS.md) and the indexes as revised between 20:36 and 20:42, after the [first review](2026-10-23-adr-0001-0004-0008-0009-review.md) and the [re-check](2026-10-23-adr-0001-0004-0008-0009-recheck.md)  
Verdict: **A thorough revision.** Fifteen of the seventeen earlier findings are resolved in the text. AMD-01 (D26/D30) remains open and is a decision for the user. AMD-08 is resolved in the text, but the code changes it describes are still pending.

The new P33 Owner Token model introduces one high and one medium finding:

- Owner-level authority becomes reachable by every CLI that Deszo launches, which run as the same user with approvals bypassed (AMD-18).
- It silently removes the separation in accepted ADR-0002 between a supervised controller and the user who approves it (AMD-19).

All amendments remain unadopted, and ADR-0008 and ADR-0009 stay Proposed.

### AMD-01 (high, still open): the decision D26 must make

ADR-0008 now says that "direct public API Run authorization alone does not decide the lifetime of unattended operational authority". That is true, but the question that remains is narrower than it sounds. §4.2 says a running workflow needs no reauthorization, and the amendment makes in-run lifecycle activation automatic once the evidence passes. So D26 must decide one thing: **whether the automatic in-run approvals of a running autonomous workflow expire**.

- If they do, a durable per-workflow wall-clock bound is needed.
- If they don't, record that D30 supersedes D26.

## New findings

### AMD-18 (high): owner-level authority is reachable by every CLI Deszo launches

P33 makes the Owner Token valid "for every current and future public Deszo API operation, regardless of … transport", with no first-party confirmation. Three facts in the current code combine with that:

- **Managed CLIs run as the user, unrestricted.** Every adapter launches with approvals and sandboxing bypassed (`--dangerously-bypass-approvals-and-sandbox`, `--dangerously-skip-permissions` in `adapters.mjs`).
- **The managed-invocation refusal works only through the bridge.** The Engine sets `DESZO_MANAGED_INVOCATION` on each invocation (`engine.mjs`). The bridge forwards that marker so the runtime can deny the call (`bridge.mjs`, `createRuntimeClient({ …, marker })`). A direct HTTP request carries no marker.
- **The client token sits in a file those CLIs can read.** Today's external token is in `runtime/connection.json`. An Owner Token pasted into an MCP client's configuration will be in a user-readable file such as the Codex or Claude configuration. The amendment keeps the plaintext out of provider environments, prompts, command lines, logs and artifacts, but not out of **files** a managed CLI can read.

Any Developer, Watcher or Judge CLI, including one following injected instructions from repository content, can therefore read the token and call the public API directly with full owner authority. It could then:

- start or approve runs;
- change settings and workspaces;
- use Context chat and recovery;
- grant **its own lineage** more diagnostic capacity.

That last one defeats ADR-0003's rule that "no workflow model result … can mint" capacity. Today the same path gives only the limited external scope, and external Run confirmation still applies. The amendment's acceptance list has no test for this path.

Required, before adopting P33:

1. **A server-side refusal that does not depend on the bridge.** On Windows, the runtime can resolve a loopback connection to its client PID (TCP table lookup, or the client-PID query for a named pipe). It can then refuse when that PID is inside a Deszo-managed Job. Platforms without an equivalent should be documented as a residual risk.
2. **Keep the token out of what managed invocations load and read by default.** Prefer the restricted native configuration (`--ignore-user-config`, `--strict-mcp-config`) so that user-level MCP registrations holding the token are not loaded. Do not store the token in plaintext configuration where an OS credential store is available.
3. **Named, individually revocable Owner Tokens**, with the token identity recorded on every mutating request, so misuse is attributable.
4. **An acceptance test:** a fixture managed invocation reads the client token and calls the API directly, and is refused.

If the user accepts the residual risk instead, P33 should say so explicitly.

### AMD-19 (medium): P33 removes ADR-0002's separation between the supervised controller and its approver

Today's first-party-only routes are listed in `runner.mjs` (`firstPartyOnly`):

- settings and workspaces;
- cache pins;
- Context chat;
- recovery;
- run-request decisions;
- **control-grant decision and revoke**;
- **incident triage**;
- `linked-repair` and `lifecycle-receipt`.

Accepted ADR-0002 relies on a first-party decision for a controller's supervision grant, and on a "first-party window extension" to prevent escalation. Under P33, the supervised controller holding the Owner Token could approve its own grant, extend its own escalation deadline, and triage its own incidents. P33 should take one of two positions explicitly:

- name these operations as protected platform invariants that only the UI can perform; or
- state that supervised control becomes self-approved, and amend ADR-0002's acceptance scenario to match.

Separately, `lifecycle-receipt` is currently a route on the public listener, protected only by the first-party guard. P33 says Host receipts are internal protocol messages with their own authenticated origin, so the route must be **reclassified and moved** before the guard is removed. Otherwise the Owner Token would authorize it. Publish the classification of every current route (public, internal or UI-only) as part of the route/credential matrix update.

### AMD-20 (low): list every writer affected by the v3 cutover

New v3 writes will receive a typed refusal, so every writer must migrate in the same release:

- the bundled editor;
- the `mcp/bridge.mjs` tool contract;
- `skills/deszo-control` and its references;
- the `scripts/deszo-*` helpers;
- the client setup in `docs/authoring`.

The capability discovery should let a client detect the new API version before its first write fails.

### AMD-21 (low): say whether the episode allowance is reserved or charged

ADR-0003's table charges "+1 unsuccessful-action capacity on admission". ADR-0009 calls it an *unsuccessful*-action allowance, which implies a charge only when the action fails. State whether admission reserves the unit and verified success releases it, or whether every admitted action consumes it.

## Recommendation

1. **Decide AMD-01** in the form stated above.
2. **Before adopting P33**, resolve AMD-18: a server-side refusal of managed callers, token storage, named tokens and the bypass test. Resolve AMD-19 as well: UI-only protected operations, and the reclassified `lifecycle-receipt` route.
3. P34 to P38 can go to their separate decisions once their small items are closed (AMD-20, AMD-21).
4. **The code work AMD-08 records remains:** isolation by physical path (PDE-R10), the protected System Self-Repair selection, and an autonomous trigger.

No ADR, register entry, code or test was changed by this review.
